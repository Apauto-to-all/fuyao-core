# 提示词分层设计

> 本文解释系统提示词的分层构建、Agent 定义加载与注册表。API 签名见 `cargo doc --workspace`。
> **调用时机**：`Engine::create_session`（主代理用途）与 `Engine::create_child_session`（子代理用途）创建 session 时，先经 `resolve_definition` 按 `SessionParams.agent_config.definition`（必填，未知名 / mode 与用途不符直接报错）加载完整 `AgentDefinition`，再调 `build_system_prompt` 取其 `system_prompt` 拼装系统提示词，结果冻结进 `Session.system_prompt`（前缀缓存红线：单次会话内不变动）。同一份 `AgentDefinition` 同时贯穿到 session 上下文供 per-session 工具可见性过滤复用，避免重复加载。每次压缩发生时也会用 `build_system_prompt` **完全重建** system_prompt 并落库（保证旧 system 中残留的动态内容在压缩后不再误导模型），此时复用 session 上下文里创建时定死的 `AgentDefinition`、用途按 `parent_session_id` 推断以保持与创建时一致。

## 覆盖区 + 补充区

系统提示词明确分为两类区域：

| 区域 | 含义 | 包含的 section |
|------|------|---------------|
| **覆盖区** | Agent 定义，可由用户文件覆盖内置默认 | Agent 身份 |
| **补充区** | 在 Agent 身份基础上追加的上下文 | 项目上下文、工具引导、技能、补充指令、环境 |

> 系统提示词在**会话创建时构建一次并冻结进数据库**（LLM 前缀缓存要求：单次会话内不变动）。

## 组装流水线

```text
resolve_definition(agent_paths, agent_config, usage) → Result<AgentDefinition, PromptError>
   │  加载 agents/{definition}.md + mode 校验；未知名 / mode 不符报错（不静默换人格），
   │  创建时定型，整 session 不可变
   │  usage: Primary（主代理 session）/ Subagent（子代理 session）
   │  同一份 definition 同时供 build_system_prompt 与 per-session 工具过滤复用
   ▼
build_system_prompt(agent_paths, definition, usage)
   ▼
build_all_sections → Vec<(标题, 内容)>
   │  按固定顺序构建各 section，空内容跳过
   │  Agent 身份层直接取 definition.system_prompt（不在本函数内重复加载）
   │  子代理索引层仅在 Primary 用途注入
   ▼
sections_to_prompt → 最终字符串
   │  每个 section 格式化为 "# {标题}\n\n{内容}"
```

## section 构建顺序

| 顺序 | section | 来源 | 区域 | 用途限制 |
|------|---------|------|------|----------|
| 1 | Agent 定义 | `agents/{definition}.md` body（用户层未命中时取同名内置定义） | 覆盖区 | 主/子均构建（按 usage 校验 mode） |
| 2 | 项目上下文 | AGENTS.md 三层叠加 | 补充区 | 主/子 |
| 3 | 工具使用指南 | 硬编码 | 补充区（内置） | 主/子 |
| 4 | 技能 skills | 运行时扫描 skills 目录 | 补充区 | 主/子 |
| 5 | 子代理 | 运行时扫描 agents 目录 + 内置默认 | 补充区 | **仅主代理** |
| 6 | 补充指令 | instructions/*.md 四层叠加 | 补充区 | 主/子 |
| 7 | 环境 | 当前时间 + 运行系统 | 补充区（内置） | 主/子 |

> Environment 是唯一**无条件加入**的 section（其余 section 空内容时跳过）。Memory 快照是占位 stub，当前不产出内容。子代理索引层只注入主代理 session——子代理不可再派生子代理（递归防护），无需此清单。

## 各 section 来源

### Agent 定义（覆盖区）

- 文件：`agents/{definition}.md`（definition 必填，由调用方显式提供定义名；要出厂人格显式传 `default`）
- 搜索层：workspace → agent → global → extra（first_exists，覆盖语义）
- 全部未命中 → `PromptError::DefinitionNotFound` 报错（附按用途过滤的可用列表），不静默替换人格

### 项目上下文（补充区）

- 文件：`AGENTS.md`（三层：workspace 根 / agent_root / 全局）
- 合并方式：merge_exists（全拼接，补充语义）
- 注意：workspace 的 AGENTS.md 在 workspace **根**（不在 `.fuyao/` 下）

### 工具使用指南

- 完全硬编码，无文件来源
- 三个子类目：文件操作 / 命令执行 / 效率原则
- 只讲使用原则，不重复 API schema（schema 由工具定义提供）

### 技能 skills

- 来源：`find_all_skills(agent_paths)` 扫描三层 + extra 的 skills 目录
- 输出：`可用 Skills：\n- {name}：{description}`

### 子代理（仅主代理注入）

- 来源：合并内置默认子代理（`explore` / `executor`）+ 用户 `agents/*.md` 中 `mode` 为 `subagent` 的定义，用户同名文件覆盖内置
- 输出：`可用子代理（subagent 工具的 subagent_type 参数可选值）：\n- {name}：{description}`，按 name 排序
- 作用：供主 Agent 调 `subagent` 工具时选取 `subagent_type`（决定子代理的人格与系统提示词）
- 仅主代理注入：子代理 session 不构建此层（子代理不可再派生，递归防护）

### 补充指令

- 文件：`instructions/*.md`（四层叠加：workspace → agent → global → extra）
- 纯正文拼接，不支持 frontmatter
- 排序：目录优先级，目录内按文件名升序

### 环境

- 当前时间（`YYYY-MM-DD HH:MM`）
- 运行系统（`std::env::consts::OS`）

## Agent 定义加载

### 文件格式

```markdown
---
name: 审查员
description: 代码审查专家
version: 1.2.0
author: Fuyao
mode: primary
tools:
  write: false
  bash: false
---

（正文作为 system_prompt）
```

frontmatter 字段全部可选（缺省 name=""、description=""、version="1.0.0"、author=""、mode=primary、tools=空）。**只有 system_prompt（body）进最终提示词**，其余是元数据。`mode` 控制定义可用于主代理还是子代理（取值：`primary` / `subagent`，缺省 primary，见下文「为什么区分主代理与子代理」）。

`tools` 控制定义层工具开关，格式与全局 `[tools.enabled]` **完全一致**（`工具名: 布尔`，未列出默认启用，显式 `false` 禁用）。它在该定义被 session 选用时收窄工具可见范围——与全局 `[tools.enabled]` 取交集（全局禁用是最高优先级硬约束，定义层只能加限制不能放开），让 LLM 压根看不到被禁工具的 schema。典型场景：只读子代理（如 `researcher`）声明 `write: false` / `bash: false`，从机制上保证最小权限，不靠提示词软约束。过滤机制与执行点详见 [工具系统设计](工具系统设计.md)。

### 加载逻辑

`load_agent_definition_from_agent_paths(agent_paths, name)` 是纯查找函数（返回 `Option`，未命中为 `None`，不做任何默认替换）：

1. `agents_def_paths(name)` 返回四层（workspace → agent → global → extra）
2. 遍历找首个存在且解析成功的用户文件（覆盖语义）
3. 用户层全部未命中 → 查内置默认表（`default` / `explore` / `executor`，编译期嵌入）
4. 内置表也无该 name → `None`

错误语义由 `resolve_definition` 统一收口：查找未命中转为 `PromptError::DefinitionNotFound`（错误信息附按用途过滤的可用定义名列表，供调用方或 LLM 直接修正）；mode 与用途不符转为 `PromptError::ModeMismatch`。

> 用户同名文件**整文件覆盖**内置默认，不合并——简单可预测。

### 内置默认

框架开箱即用自带三份内置 Agent 定义，通过 `include_str!` 编译期嵌入二进制（运行时零读盘、零资产依赖）：

| name | 用途 | mode | 文件 |
|------|------|------|------|
| `default` | 主 Agent 默认人格 | all | `defaults/primary/default.md` |
| `explore` | 只读探索子代理 | subagent | `defaults/subagent/explore.md` |
| `executor` | 通用执行子代理 | subagent | `defaults/subagent/executor.md` |

内置定义与用户定义同名同权——`default.md` 的内容即出厂人格正文，文件是唯一来源，改文件即改人格，无需同步两处。修改内置默认需重新编译；用户的自定义定义走运行时读盘，不受此限制。内置 .md 解析失败直接 panic：编译期嵌入内容受开发者完全掌控，解析失败属开发期 bug，应尽早暴露。

### 默认 Agent

`definition` 必填，没有「未指定时用默认」的隐式兜底：要出厂人格就显式传 `default`（`fuyao_api::DEFAULT_DEFINITION_NAME` 常量）。查找顺序与任意定义名一致——用户 `agents/default.md` 覆盖内置 `default`，都无则命中内置。`default` 是框架保证恒存在的唯一定义名（内置表最低优先级注入，用户文件只能覆盖其内容、不能让这个名字失效），产品层据此把它固定为开箱默认人格。

## AgentRegistry

扫描 `fuyao-agents/` 目录（全局层 + 工作区层），提供列举 / 查询 / CRUD。

| 操作 | API | 说明 |
|------|-----|------|
| 列举 | `list(page, size, scope, q)` | 分页 + 作用域过滤 + 关键字搜索 |
| 查询 | `get(id)` | 按 `global/{名}` / `workspace/{名}` / `default` 定位 |
| 读取内容 | `read_content(source, name)` | 读 system.md + fuyao.toml 文本 |
| 写入内容 | `write_content(source, name, file, content)` | 覆盖写 system.md 或 fuyao.toml |
| 创建 | `create(source, name)` | 创建空文件夹（编辑时按需创建文件） |

> 容错策略：空文件夹立即可见、可编辑（无 system.md 时 name=文件夹名，system_prompt 用全局默认）。
>
> **无删除操作**：AgentRegistry 支持 create / read / write / list / get，但**不支持 delete**——删除 Agent 定义需手动移除目录。

### 名称校验

拒绝：空串 / 纯空白、超长（>255）、含 `/ \ ..`、Windows 非法字符（`< > : " | ? *`）、Windows 保留名（CON / PRN / NUL 等）、保留字 `default`。

## 关键设计决策

### 为什么系统提示词冻结进数据库？

LLM 前缀缓存：如果会话中途系统提示词变化，之前缓存的 token 前缀全部失效，每次请求重新计算全量。冻结后，整个会话复用同一前缀缓存，大幅降低延迟和成本。

### 为什么项目上下文用叠加而非覆盖？

AGENTS.md 是项目规范——全局层给通用规范，工作区层给项目特定规范。两者应该共存（叠加），而非后者替换前者。Agent 定义则是人格——高优先级覆盖低优先级（你不会同时是两个角色）。

### 为什么工具引导硬编码而非可配置？

工具引导是使用原则（read 先确认 / bash 慎用 / 并行读），这些是框架设计理念的一部分，不是用户可配置项。用户可以通过 instructions/ 补充自己的工具使用规范。

### 为什么 AgentRegistry 合并了 list 和 detail？

Rust 解析 md/toml 足够快。合并后前端列表展开直接复用列表数据，省一个详情接口和一次网络请求。

### 为什么未知名报错而非回退默认人格？

定义名是调用方显式提供的输入，静默回退意味着把「调用方想要 A 人格」偷换成「跑成了默认人格」——拼写错误（如 `defualt`）不报任何错，会话照常进行但人格错了，对以人格为核心语义的产品是正确性黑洞。显式报错并附可用列表，把错误挡在会话创建之前；出厂人格 `default` 本就是一等定义（列举可见、按名可调），显式传名的成本为零。

### 为什么区分主代理与子代理？

Agent 定义通过 frontmatter `mode` 字段区分使用场景：`primary`（只能作主代理，缺省值）、`subagent`（只能由子代理工具派生），二者二分、职责互斥。系统提示词构建时按**用途方向**做对称校验（由 `PromptUsage` 决定，主代理 session 校验 `is_usable_as_primary`，子代理 session 校验 `is_usable_as_subagent`）——用途与 mode 不符时返回 `PromptError::ModeMismatch` 报错拒绝，不做静默人格替换。这样既防止把专门的子代理人格误用作主代理，也防止把专属主代理人格误派生为子代理。缺省 primary 保证主代理人格不会误闯子代理列表——子代理列表只含专职子代理。

子代理的派生与选择由 `subagent` 工具承载：工具参数 `subagent_type`（必填）指定用哪个子代理定义，引擎据此加载 `agents/{subagent_type}.md` 构建子 session 的系统提示词。主 Agent 通过系统提示词中的「子代理」索引层得知可选的 `subagent_type` 取值（内置 `explore` / `executor` + 用户自定义），从而正确填参。子代理索引只注入主代理 session——子代理不可再派生子代理（递归防护）。

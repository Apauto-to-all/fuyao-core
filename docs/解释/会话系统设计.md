# 会话系统设计

> 本文解释 SQLite 持久化、上下文压缩、费用统计、标题生成等会话相关机制。API 签名见 `cargo doc --workspace`。

## 经引擎内核直接持有

会话持久化由**引擎内核直接持 `SessionStore`**：

```text
Engine.store: Arc<SessionStore>
  ├─ 引擎启动时用 agent_paths 找到并打开数据库
  ├─ 引擎持有连接池，所有 session 共享同一份
  └─ 每个 session task 拿 Arc<SessionStore> clone 引用，用 session_id 在同一库里读写自己的历史
```

## SessionStore：持久化层

```text
SessionStore（SQLite 连接池）
  ├─ new(db_path)        打开 + 初始化 schema（参数从 get_config().session.storage 读）
  ├─ pool()              共享连接池（供兄弟模块复用，如 fuyao-tools 的 TodoStore 自建独立池）
  ├─ create / get / update / delete / list_all(workspace_filter, limit, offset) / count / count_with_filter   Session CRUD（只维护 sessions 表元数据；update 落库时经 unixepoch() 刷新 last_active_at；list_all 按 last_active_at 倒序 + 可选按 workspace 过滤）
  ├─ insert_message     单条 INSERT（事件级落库，事务内分配 seq + 回填 msg.seq）
  ├─ count_messages     消息计数
  ├─ load_visible_messages  按 seq >= last_compacted_seq 过滤的可见窗口
  ├─ load_full_history   全量历史（含压缩前的旧消息，仅审计用）
  ├─ mark_compaction     插 compaction 边界消息 + 更新 last_compacted_seq
  ├─ update_system_prompt / update_title / end_session   单字段 UPDATE
  └─ disconnect / close  连接池关闭
```

## SQLite 存储配置

- per-agent 隔离：每个 agent_id 独立的 sessions.db（见 [Agent 身份与路径设计](Agent身份与路径设计.md)）
- 连接池：`max_connections`（默认 5，可配）
- busy_timeout：默认 5s
- WAL 模式（高并发读写）+ 外键启用

配置：`[session.storage]`（见 [配置项参考](../参考/配置项参考.md)）。

## 表结构（2 张表 + 版本表）

```text
sessions（会话元数据）
├── id                TEXT PK       会话 ID（8 位 UUID 截断）
├── started_at        REAL NOT NULL  开始时间戳
├── ended_at          REAL           结束时间戳
├── end_reason        TEXT           结束原因（Engine::end_session 传入）
├── message_count     INTEGER       消息总数（内存计数器维护）
├── tool_call_count   INTEGER       工具调用总数
├── total_prompt_tokens      INTEGER  累计输入 token
├── total_completion_tokens  INTEGER  累计输出 token
├── total_reasoning_tokens   INTEGER  累计推理 token
├── total_cached_tokens      INTEGER  累计缓存 token
├── total_cost        REAL          累计费用
├── title             TEXT          会话标题
├── system_prompt     TEXT          系统提示词（冻结，压缩时重建）
├── compression_count      INTEGER  压缩次数
├── last_compacted_seq     INTEGER  最近压缩边界消息的 seq（NULL = 从未压缩）
├── parent_session_id      TEXT  通用子任务标记（NULL = 主 session；非 NULL = 子任务 session，值为父 session id）
├── workspace              TEXT  工作目录绝对路径（创建会话时定死，分隔符归一化为正斜杠；NULL = 无工作目录）
└── last_active_at         REAL NOT NULL  最近活动时间戳（创建时 = started_at；每次 update 落库经 SQLite unixepoch() 刷新）

messages（消息）
├── id                INTEGER PK AUTOINCREMENT
├── session_id        TEXT NOT NULL FK→sessions.id
├── model_id          TEXT          模型 ID（assistant 消息携带）
├── role              TEXT NOT NULL  user/assistant/system/tool/developer
├── content           TEXT          消息内容
├── reasoning         TEXT          推理内容
├── tool_call_id      TEXT          工具调用 ID（tool 角色）
├── tool_calls        TEXT          工具调用列表（JSON，assistant 角色）
├── tool_name         TEXT          工具名称
├── prompt_tokens / completion_tokens / reasoning_tokens / cached_tokens  INTEGER  单条 token 用量
├── cost              REAL          单条费用
├── finish_reason     TEXT          stop/tool_calls/length/interrupted
├── timestamp         REAL NOT NULL
├── seq               INTEGER NOT NULL  session 内单调递增投影序号
├── kind              TEXT NOT NULL DEFAULT 'message'  message/compaction
└── UNIQUE(session_id, seq)         唯一约束（防重复 seq）

schema_version（版本管理）
└── version           INTEGER       当前版本 1
```

### 索引

| 索引 | 表 | 列 | 用途 |
|------|----|----|------|
| `idx_sessions_started` | sessions | started_at DESC | 按创建时间列会话 |
| `idx_sessions_last_active` | sessions | last_active_at DESC | 按最近活动倒序列会话 |
| `idx_messages_session` | messages | (session_id, timestamp) | 按时间取会话消息流 |
| `idx_messages_session_seq` | messages | (session_id, seq) | 压缩可见窗口过滤 |
| `idx_messages_session_kind_seq` | messages | (session_id, kind, seq) | 按 kind 过滤 + seq 排序 |

> token 冗余设计：messages 存单条 token，sessions 存累计 token（`accumulate_session_total` 逐条累加维护）。

## 消息可见性（compaction 边界）

`kind='compaction'` 的消息是上下文压缩产生的边界点，其 `content` 字段存摘要正文。

- `MessageKind::Message`：普通消息（user / assistant / system / tool），默认 kind
- `MessageKind::Compaction`：压缩边界消息（content = 摘要正文）

模型可见窗口靠 SQL `seq >= last_compacted_seq` 过滤——`load_visible_messages` 返回 `[最近一条 compaction 边界, ...之后的消息]`。

## 上下文压缩

### 一句话机制

> session_id 永不变，压缩 = 在 messages 表插一条 `kind='compaction'` 边界消息 + 更新 sessions 元数据 `last_compacted_seq` 指针，模型可见窗口靠 SQL `seq >= last_compacted_seq` 过滤。

- 不创建新 session
- 不删除旧消息（旧消息物理保留在 DB，可审计可恢复）
- 不重置统计（token 累计反映对话真实消耗）

### 触发位置：pre-turn（主循环内部）

```text
run_session 主循环：
  loop {
    consume guide（inject_messages 经 emit_to_history 把队列消息落 DB）
    run_pre_turn_compression(...)   ← 阈值检测：上轮 usage / (context_length - summary_max_tokens) ≥ threshold → 触发
    run_turn                        ← ReAct 循环（与压缩无关）
  }
```

**为什么是 pre-turn 而非 post-turn**：上一轮真实 usage 在 turn 结束就拿到了，pre-turn 用它判定阈值——省一次必爆的请求。turn 边界是干净同步点，无流式、无工具执行。

**为什么不开新队列/通道**：压缩是主循环 pre-turn 主动触发的内部重写，task 内串行天然互斥，不需要锁、不需要信号、不需要识别 LLM 输出。

**子代理 session 默认不触发压缩**：`run_pre_turn_compression` 入口按 `session.parent_session_id.is_some() && [session.compression].skip_child` 早退。子代理以 `Fresh` 模式派生、一次性运行，只把最终回复文本作为 tool_result 回喂父 Agent，自身完整历史留在子 session 内。若允许子代理中途压缩，早期工具证据会被摘要替代，失真的最终回复会传导给父 Agent 的决策；且压缩需额外调一次摘要 LLM，对一次性子代理在成本与质量上均不划算。该豁免可配置（`skip_child` 默认 `true`，与标题生成的 `skip_child` 同模式）。

### 触发阈值

```text
prompt_tokens ≥ threshold × (context_length - summary_max_tokens)
```

- `prompt_tokens` 来自上一轮 LLM 返回的真实 usage
- `context_length` 从 `ModelConfig.limit.context` 解析；解析不到时回退 `fallback_context`（默认 128000）
- `summary_max_tokens` 作为输出预留扣除

### 关键不变量（红线）

| 红线 | 含义 |
|------|------|
| **摘要请求消息原样发** | 前缀缓存生命线——`ChatRequest.messages` 就是 session 当前 messages 原样转换，末尾追加一条 user 消息（摘要指令），强制 `tools=[]`。system 一字不动。前缀缓存 100% 命中 |
| **session_id 永不变** | 压缩不创建新 session，靠插边界消息 + 更新指针实现 |
| **压缩归属 fuyao-session** | core 只编排事件，session 提供 `generate_summary` / `apply` |
| **失败 log warn 跳过** | 摘要 LLM 失败、摘要为空、落库失败等都只 warn，不阻塞主对话 |

### 动态保留窗口

```text
实际保留 = min(context_length × keep_ratio, keep_tokens_max)
```

- `keep_ratio`（默认 0.05）：保留比例
- `keep_tokens_max`（默认 8000）：上限，防止极端场景保留过多

例：32K 模型 → 1600，128K 模型 → 6400，200K+ 模型 → 8000（被 max 截断）。

### 反抖动闸门

`CompressionRuntimeState` 记录连续两次压缩的节省比例。如果都低于 `min_savings_pct`（默认 10%），下次 `should_compress` 直接返回 false——避免「压了又压还是这么大」的死循环烧钱。

### 手动压缩（InputEvent::Compress）

自动压缩是「引擎按阈值自决」的被动路径；手动压缩是「用户 / 上层应用主动发消息请求」的主动路径。二者**共用同一套压缩执行流程**（摘要 LLM 调用 + 落库 + 三阶段事件），区别只在触发入口与是否过阈值门：

| 维度 | 自动压缩 | 手动压缩 |
|------|---------|---------|
| 触发方 | 引擎按阈值自决 | 用户 / 上层主动发 `InputEvent::Compress` |
| 阈值检测 | 必须满足（prompt_tokens ≥ 阈值比例） | 跳过——用户明确要压，不判阈值 |
| 反抖动 | 连续低效压缩被闸门拦 | 跳过——用户决策优先 |
| 子会话豁免 | 生效（`skip_child` 默认 true） | 不适用——用户意图优先，引擎照做 |
| 触发原因 | `auto` | `manual` |

核心原则：手动压缩是用户意图的直接表达，不经过「该不该压」判定，但仍复用「怎么压」的执行链路。手动压缩消息经引擎入口送入控制通道（属四类消费语义中的 B 类——命令主循环做事），主循环在 turn 边界消费（不抢占在途 turn，等当前 turn 跑完再处理），随后直接调一次压缩执行体（reason = `manual`）。引擎忠实执行每一条压缩命令，不做同批次去重 / 合并——连续发送多条 `Compress` 会触发多次压缩（去重是上层职责，引擎不替外部解释意图）。三阶段 Compression 事件照常发出，`reason` 字段标记为 `manual`，前端无需新增渲染逻辑——这与「消息驱动」架构一致：手动压缩是一条输入消息触发的消息流分支，而非新 API。

### apply 的 keep_recent 复制为新 seq

`apply` 函数做两件事：

1. 调 `mark_compaction` 写 compaction 边界消息（seq = N+1）
2. **把 keep_recent 复制成新 seq 重新 INSERT 进 DB**

为什么需要复制：改成 DB 模式后，`load_visible_messages` 用 `seq >= last_compacted_seq`（即 seq >= N+1）查询，keep_recent 的 seq 都 < N+1 会被过滤掉——丢失近期上下文。复制成新 seq 后下次 `load_visible_messages` 自然返回 `[compaction 边界] + [keep_recent 副本]`。

**已知设计权衡**（非 bug，agent 运行时路径不受影响）：

- **审计重复**：`load_full_history` 会返回重复内容（原 seq + 副本），多次压缩复合放大。生产代码不调用 `load_full_history`，仅影响审计/导出场景。
- **部分失败一致性**：`mark_compaction` 与副本 INSERT 不在同一事务，中途失败会留下「边界已落、副本残缺」状态。react/mod.rs 对 apply 失败仅 warn 跳过，不回滚。

### 事件协议：三阶段 Compression 事件

单一 `OutputEvent::Compression` 事件变体 + 内部 `payload` 区分三阶段（对齐 `UserMessage + UserMessageMode` 模式）：

```text
Compression::Started { reason, prompt_tokens, context_length }   ← 调摘要 LLM 之前
Compression::Delta   { content?, reasoning? }                     ← 摘要流式增量（live-only）
Compression::Ended   { reason, content, tokens_before/after, new_seq }   ← apply 落库成功后
```

流式 Delta 通过「同步 callback + tokio::mpsc channel + tokio::select!」跨层转发。`generate_summary` 用 `stream_chat()` 让前端实时看到摘要生成。

**压缩复用 session 当前模型的全套配置**：调 `generate_summary` 时传入的 `model_id` 与 `options` 取自 session 当前轮 resolved 的真值（model + thinking_type + reasoning_effort 原样带），唯一差别是**强制禁用工具**（函数内部 `options.tools = None` / `options.tool_choice = None`——压缩是独立摘要流，不进 ReAct，不能让模型调工具）。system / messages 原样不动，保住前缀缓存。

### system_prompt 重建钩子

每次压缩发生时，用 `build_system_prompt(agent_paths, agent_config)` **完全重建** system_prompt 并落库 + 写回内存 session——保证旧 system 中残留的动态内容（如「基于刚才的 X 错误继续排查」）在 X 已被压进摘要后不再误导模型。`build_system_prompt` 是纯本地文件拼接（不调 LLM），成本低。

### 不实施的项（明确决策）

| 项 | 决策 | 理由 |
|----|------|------|
| **Provider 413 被动压缩** | 不做 | 413 多为模型切换导致的用户使用错误（128K 模型跑到 100K 切到 8K），引擎不应替用户兜底；按「引擎 fail loud + 上层应用决策」原则，413 直接报错让上层处理 |
| **工具语义压缩** | 不做 | fuyao 用 MCP 工具为主，没有内置 per-tool 摘要模板的土壤；工具结果压缩应归工具自身实现 |
| **Focus topic** | 不做 | 无人值守场景不需要用户可控压缩方向 |
| **失败恢复分级** | 暂不做 | 已落未来计划，作为统一基础设施待启动 |
| **出站事件 per-session 化** | 暂不做 | 等真出反压问题再做 |
| **durable 事件持久化** | 不做 | events 表 / EventStore 是过度设计，"投影成消息"已由 apply 的 mark_compaction 实现 |

## 费用统计（cost）

**每条 assistant 消息（无论是否含工具调用）独立计费**并累积进 `session.total_*`。不发任何事件（cost 只进 DB）。

### 计费时机

`accumulate_usage_and_cost` 在两个 assistant 消息产出点调用（`emit_to_history` 内 push 之前）：

- `handle_final_reply`：最终回复轮（finish_reason=stop）
- `handle_tool_calls`：工具调用轮（finish_reason=tool_calls）

### 计费公式

```text
费用 = 输入费用 + 输出费用 + 缓存费用

输入费用 = (prompt_tokens - cached_tokens) × input_price / 1M
输出费用 = 按 reasoning_price 是否存在分两种：
  ① reasoning_price 存在且 ≠ output_price：
     non_reasoning = completion - reasoning
     输出 = non_reasoning × output_price + reasoning × reasoning_price
  ② reasoning_price == output_price 或不存在：
     输出 = completion × output_price
缓存费用 = cached_tokens × cache_price / 1M
```

- **缓存 token 扣除**：输入费用排除缓存命中部分（`prompt - cached`），缓存单独按 `cache_price` 计费
- **梯度价格 tier**：`tiers` 按 `max_tokens` 排序，取第一个 `prompt_tokens ≤ tier.max_tokens` 的区间，无匹配取最后一个。tier 内有值的字段覆盖平铺价格
- **Decimal 精确计算**：用 `rust_decimal::Decimal` 避免 f64 加法误差，累积时再转 f64

### 为什么每条 assistant 都计费（含工具调用轮）？

每次 `provider.stream_chat()` 都是一次独立的付费 API 调用，OpenAI 按全量 prompt 计费——「重叠 prompt 重复计费」是计费事实，不是 bug。

详见 [Provider 设计](Provider设计.md)。

## 标题生成（title_generator）

首轮对话结束后 fire-and-forget 异步生成简短标题（3-7 词），写回 DB 并发 Title 事件给前端。

### 流程

```text
handle_final_reply 末尾（persist 之后）
   ↓ 判定首轮（user 消息计数 == 1）
   ↓ tokio::spawn fire-and-forget 任务
maybe_generate_title（fast 模型优先 → 主模型回退 → 放弃）
   ↓ SessionStore::update_title（单字段 UPDATE）
dispatch::dispatch 发 OutputEvent::Title（经拦截/发送/观察管道）
```

### 关键设计

- **fire-and-forget**：不阻塞主 ReAct 循环（LLM 调用 1-3 秒甚至超时）；多 session 并发天然安全（各 spawn 独立）
- **模型优先级**：`[models.fast]` → 主模型 → 放弃（fast 可能跨 Provider 配置）。**只取 fast 的 model_id 选模型，不取其 thinking**
- **LLM 调用方式**：非流式 `provider.chat()`（标题是短文本，无需流式增量——区别于 compressor 的 `stream_chat()`）。恒传默认 options（thinking 两字段为 None）——**标题固定不思考**
- **首轮判定**：user 消息计数 == 1（计数法，比 `title=="新会话"` 稳——用户可能改过 title）
- **失败处理**：LLM 失败 → `maybe_generate_title` 返回 None（fast 失败自动回退主模型）；落库失败 → warn 跳过；都不阻塞主流程
- **Engine::shutdown 时 spawn 还在跑**：不阻塞 shutdown（独立 task，runtime 关闭自然终止）；标题未落库不影响下次启动（resume 读 DB 旧 title）

### 三者独立（禁止绑定）

`[models.fast]` / `Provider::chat` / 标题生成是三个毫不相关的东西，仅在本功能恰好同框：

- `[models.fast]` 是一条模型配置（model + thinking_type + reasoning_effort 三字段），独立存在
- `Provider::chat` 是 Provider 的非流式方法（接受 options），独立存在
- 标题生成恰好读 fast 的 **model_id** 选模型、恰好调 `chat()` 走非流式，但**不读 fast 的 thinking**、调 chat 恒传默认 options

禁止把三者绑成一条「标题专用链路」。标题固定不思考源于标题自身设计，与 fast 配不配思考、chat 支不支持 options 都无关。

## Todo 管理（TodoStore）

todo 的 `TodoStore` 位于 `fuyao-tools`（不在 fuyao-session）：

```text
TodoStore（fuyao-tools/src/todo/store.rs）
  ├─ 自建独立 SqlitePool（与 SessionStore 共用同一个 sessions.db，WAL 多连接安全）
  ├─ 自带 TODOS_SCHEMA_SQL（CREATE TABLE IF NOT EXISTS todos，不加 FK，按 session_id 字符串隔离）
  └─ TodoItem { id, content, status }
```

状态机约束：同时只能一个 `in_progress`，顺序 = 优先级。经 `todowrite` 工具操作（见 [工具系统设计](工具系统设计.md)）。

**为什么 todo 自建独立池**：工具层经 `ToolCallContext` 只能拿到 `agent_paths`（`execute_tools` 故意只收 `&AgentPaths` 不收 store），把池传进去要改 `fuyao-api` 的 `ToolCallContext` 把 sqlx 拖进 L0（违反瘦身原则）。方案 A（独立池 + 同 sessions.db）零架构侵入，契合现有边界。

## 关键设计决策

### 为什么 messages 不在内存（事件级落库）？

每个 session task 永不退出，若持有 `messages: Vec<Message>` 内存常驻会随历史线性增长——多 session 并发时内存压力大。改成 DB only 后：

- 单个 session 内存占用恒定（元数据几十 KB，不随历史增长）
- 多 session 并发无内存压力
- 崩溃恢复能力提升（消息产生即落库，turn 中途崩溃仅丢当前 in-flight 事件，不丢整轮）

task 骨架本身（栈 + SessionCtx + Session 元数据）只占恒定几十 KB，与 messages 无关——所以**决议不做 turn 完 task 退出 + 懒 resume**（与「恢复需明确触发」原则冲突），让 task 永不退出，只把 messages 砍到 DB。

### 为什么经引擎直接持有？

会话持久化是引擎内核的协作者。直接持有 `SessionStore` 让引擎内核：

- 事件级落库有统一写入入口（`emit_to_history`）
- DB 句柄共享给所有 session task 零成本
- 不经 hook 间接调用，减少 dispatch 管道外的复杂度

### 为什么 per-agent 隔离 sessions.db？

不同 agent_id 是独立 Agent 实体（数据隔离单元）。它们的会话历史不应交叉——coder 的对话不应出现在 reviewer 的会话里。per-agent 隔离确保数据安全。

### 为什么加 workspace / last_active_at 两个字段？

同一 agent（同一 sessions.db）下，不同工作目录创建的会话会混在一张表里；用户希望列表像即时通讯那样「最近聊的排最前」并能「切到某项目只看该项目的会话」。两个诉求各对应一个字段：

| 字段 | 解决的诉求 | 生命周期 |
|------|-----------|---------|
| `workspace` | 按工作目录过滤 | 创建会话时定死，取自引擎的 `agent_paths.workspace`，归一化（分隔符统一为正斜杠）后落库；无工作目录时为 NULL |
| `last_active_at` | 按最近活动倒序 | 创建时 = started_at；每次 `update` 落库经 SQLite `unixepoch()` 刷新为当前时间 |

**为什么 last_active_at 用 SQL `unixepoch()` 而非由调用方传值**：`update` 的调用方（turn 边界 persist）拿到的是 `&Session`（不可变借用），若在 Rust 侧刷新字段要改签名、改所有 persist 调用点。让 DB 在 `UPDATE` 语句内自动刷新，零调用点改动；内存对象虽持有旧值，但列表查询本就从 DB 读，下次 `get` / `list_all` 取到的就是刷新后的值，内存与 DB 不会产生可见的不一致。count 类统计字段（`message_count`）与消费类字段（token / cost）的 update 语义不受影响。

**为什么不存项目可读名称（目录名）**：可由 workspace 路径推导（取末级目录名），单独存会冗余且易不一致，故不存。

### 为什么压缩用边界消息 + 指针？

边界消息 + 指针方案：session_id 永不变、旧消息物理保留可审计、统计字段不重置、可见性靠 SQL 过滤。

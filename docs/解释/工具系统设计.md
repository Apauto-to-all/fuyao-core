# 工具系统设计

> 本文解释工具系统的三层架构、注册机制、安全防护与执行编排。API 签名见 `cargo doc --workspace`。

## 三层架构

工具系统跨三个 crate，职责严格分离：

| 层 | crate | 职责 |
|----|-------|------|
| 类型层 | fuyao-api | 纯类型定义（ToolDefinition / ToolFn / ToolResult / ToolCallContext），零逻辑 |
| 实现层 | fuyao-tools | 内置工具实现 + 安全防护 + 静态注册表 |
| 编排层 | fuyao-core | 工具执行调度（orchestrate + executor） |

调用链：`fuyao-app::setup` 注册工具 → ReAct 循环中 LLM 返回 ToolCalls → `orchestrate` 调度 → `executor` 串 / 并行执行 → 结果经 dispatch 管道推送。

## 工具定义（ToolDefinition）

发给 LLM 的工具定义遵循 OpenAI Function Calling 规范，三层嵌套：

```text
ToolDefinition              ← type="function"
  └─ ToolSchema             ← name + description + parameters
       └─ ToolParameters    ← type="object" + properties + required
```

参数属性（ToolParameterProperty）支持 type / description / default / enum / items。只实现 Serialize（单向发给 LLM，不反序列化）。

## ToolFn：boxed async closure

```text
ToolFn = Arc<
    dyn Fn(serde_json::Value, ToolCallContext)
        -> Pin<Box<dyn Future<Output = String> + Send>>
    + Send + Sync
>
```

不是 trait，不是裸 fn pointer——是 Arc 包装的 boxed async closure 类型别名。

- **Arc**：handler 被 clone 到并行任务中
- **Pin<Box<dyn Future>>**：统一不同闭包的 Future 类型
- **返回 String**：工具结果序列化为 JSON 字符串

## 工具注册

### 编译期注册 + 运行期过滤

```text
fuyao-tools/src/registry.rs:
  static TOOL_REGISTRY: LazyLock<HashMap<&'static str, ToolEntry>>
```

首次访问时初始化，进程内单例。每个 category 模块暴露 `register(&mut map)` 注册子工具。

`fuyao-app::setup` 的注册流程：
1. `all_tools()` 取全部注册工具
2. `handle.register_tool(name, schema, handler)` 注入引擎

> **过滤下沉到注册漏斗**：`[tools.enabled]` 的过滤不在 app 层 `register_builtin_tools` 做，
> 而是下沉到 `EngineHandle::register_tool` 漏斗入口（第一道检查即 `is_tool_disabled`）。
> 这样所有工具来源（内置 / MCP / app 层动态注册）统一受控，无需各调用方各自过滤。

> **规则：默认全开。** 未在 `[tools.enabled]` 列出的工具默认启用，只有显式 `false` 才禁用。

### ToolEntry

```text
ToolEntry = { definition: ToolDefinition, handler: ToolFn }
```

极简二元组：Schema（给 LLM）+ Handler（框架执行）。无元数据、无优先级——可见性通过 `[tools.enabled]` 外部控制。

## 安全防护（纵深防御）

### 路径安全（check_sensitive_path）

五层检查依次短路：

| 层 | 规则 |
|----|------|
| 1 | `FUYAO_WRITE_SAFE_ROOT` 白名单（环境变量设置时生效） |
| 2 | 敏感路径前缀（`/etc/` `/boot/` `/sys/` `/proc/` `/dev/` `C:\Windows\` 等） |
| 3 | 敏感系统文件（`/etc/passwd` `/etc/shadow` `/etc/sudoers` `sshd_config` 等） |
| 4 | 用户主目录敏感文件（`~/.ssh/id_rsa` `~/.bashrc` `~/.gitconfig` `~/.npmrc` 等） |
| 5 | 特殊文件名（`.env` `.htpasswd` `authorized_keys`，任意位置） |

配套防护函数：

| 函数 | 防什么 | 用在哪 |
|------|--------|--------|
| `is_internal_path` | 框架内部路径（`.fuyao/.env`），防 prompt injection | read 工具 |
| `has_binary_extension` | 31 种二进制扩展名（`.exe .png .pdf .zip .db .so` 等） | read 工具 |
| `is_blocked_device` | 设备文件（`/dev/zero /dev/random /dev/tty` 等 12 个 + `/proc/self/fd/*`） | read 工具 |

### 命令安全（check_command_safety）

两级阻断：

| 级别 | 模式 | 示例 |
|------|------|------|
| critical | 确定性高危 | `rm -rf`、`dd of=/dev/sd*`、`mkfs.*`、fork 炸弹 |
| medium | 系统级风险 | `curl|sh`、`shutdown`、停关键服务 |

> **设计哲学**：不做完整 Guard，只拦确定性高危。其余放行让 Agent 自主决策。

配套：`validate_workdir`（白名单字符校验，挡 shell 注入）、`build_safe_env`（屏蔽 API key 环境变量，防泄漏）。

### 脱敏（redact_sensitive_text）

七组正则（fancy_regex）：API key 前缀 / 环境变量赋值 / JSON 字段 / Auth header / 私钥块 / 数据库连接串 / JWT。

应用点：read / grep / bash 输出，防止泄漏。

### 文件追踪（去重 + 外部编辑检测）

read / write / edit 工具共享一套文件追踪器（基于 mtime 时间戳）：

| 机制 | 用在 | 行为 |
|------|------|------|
| **去重检测** | read | 已读且未修改的文件再次读取时提示"内容未变"，避免 LLM 浪费轮次 |
| **外部编辑检测** | write / edit | 写入前比对 mtime，若文件自上次跟踪后被外部修改，返回 warning（不阻断）——防止覆盖用户的手动改动 |

> 这是"建议而非阻止"的设计——工具仍执行操作，但让 LLM 知道潜在风险。

## 工具执行编排

### orchestrate 流程

```text
LLM 返回 ToolCalls
    │
    ▼
读 [tools.runner] 配置
    │
    ▼
should_parallelize? ─── 判定（见下）
    │
    ├── 是 → execute_parallel（Semaphore 限流 + JoinSet 管理）
    └── 否 → execute_sequential（逐个 await）
    │
    ▼
每个工具：execute_single_tool
    │  handler.get(name) → 未找到返回 "未知工具: xxx"
    │  JSON 反序列化 args → 失败回退 Null
    │  构造 ToolCallContext → handler(args, ctx).await
    │
    ▼
结果经 dispatch 管道推送 OutputEvent::ToolResult
    │
    ▼
continue ReAct 循环（工具结果回喂 LLM）
```

### 并行 / 串行判定（should_parallelize）

四步短路：

| 步 | 条件 | 结果 |
|----|------|------|
| 1 | 工具数 ≤ 1 | 串行 |
| 2 | 任一工具在 `never_parallel` | 串行 |
| 3 | `path_scoped` 工具的路径重叠 | 串行 |
| 4 | 非 path_scoped 工具在 `parallel_safe` | 并行 |

默认：`never_parallel = ["bash", "todowrite"]`、`parallel_safe = ["read", "glob", "grep", "skill", "webfetch"]`、`path_scoped = ["read", "write", "edit"]`。

### 并行执行设计

- **Semaphore**：限制最大并发（默认 8），超出排队
- **JoinSet**：管理 spawned 任务，drop 时自动 abort 未完成任务（防泄漏）
- **mpsc channel**：完成一个收集一个，结果顺序 = 完成顺序（非调用顺序）

## 关键设计决策

### 为什么类型 / 实现 / 编排三层分离？

类型层零逻辑（fuyao-api 纯定义），实现层不知道何时被调用（fuyao-tools），编排层不知道工具内部细节（fuyao-core）。三者正交，可独立测试，替换一层不影响其他。

### 为什么 ToolFn 用 boxed closure 而非 trait？

trait object 需要定义 trait + impl，每个工具都要写样板。boxed closure 直接用闭包注册，简洁。Arc 确保跨任务 clone 廉价。

### 为什么未注册工具不 panic？

返回 `"未知工具: xxx"` 让 LLM 自己决策（可能是模型幻觉了不存在的工具）。符合"自主决策"原则——错误信息含明确建议，避免卡死。

### 为什么 bash 在 never_parallel？

bash 有副作用（文件修改、网络请求），并行执行可能导致竞态。todowrite 是覆盖写，并行会互相覆盖。只读工具（read / glob / grep）可安全并行。

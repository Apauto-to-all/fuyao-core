# 工具系统设计

> 本文解释工具系统的三层架构、注册机制、安全防护与执行编排。API 签名见 `cargo doc --workspace`。

## 工具注册 vs 工具执行（关键边界）

工具有两个层面的职责，生命周期完全不同，**绝不能混为一谈**：

| 层面 | 职责 | 归属 | 生命周期 |
|------|------|------|---------|
| **工具注册** | 有哪些工具、每个工具的 schema 和 handler | **引擎级**（共享） | 启动时装配一次，所有 session 共享同一份 `ToolRegistry` |
| **工具执行** | 真的去跑某个工具调用 | **session 级**（各跑各的） | 各 session 的 ReAct 循环里发生，互不等 |

```text
引擎级（共享，启动时装配）：
  ToolRegistry: { "read": entry, "bash": entry, ... }
        │
        │  所有 session 共享这份注册表（Arc<ToolRegistry>，只读）
        ▼
Session 级（独占，各自的执行）：
  task A 的 ReAct：LLM说调read → 从注册表查 entry → 在 A 的 task 里执行 → 结果进 A 的历史
  task B 的 ReAct：LLM说调bash → 从注册表查 entry → 在 B 的 task 里执行 → 结果进 B 的历史
```

**为什么执行归 session 而不归引擎**：如果把执行也放引擎级，引擎就要管理"哪个 session 的哪个工具调用在跑"，变成全局调度器——违背"引擎不为工具调用建全局队列、不排队、不协调"的原则。引擎的职责到"提供注册表、让各 session 能查到 handler"为止，执行是各 session task 自己的事。

### 工具结果不走队列

工具结果虽然是"消息"，但它的**来源和生命周期**与用户消息根本不同，**不经过 session 的消息队列**：

| | 用户消息（InputEvent） | 工具结果 |
|---|---|---|
| **来源** | 外部（调用方经单一入口送进来） | ReAct 循环内部产生的 |
| **生命周期** | 跨越多轮，可能排队等待 | 单轮内部，产生即被消费 |
| **走向** | 经 tx_inbound 通道 → task 取出 | 直接进 task 的 DB（事件级落库） |

工具结果是 task 自己同步 await 出来的中间产物，产生时 task 正握着控制权，没有别的 task 会碰，**不需要队列协调**。

详见 [引擎内核设计](引擎内核设计.md)。

## 三层架构（类型 / 实现 / 编排）

工具系统跨三个 crate，职责严格分离：

| 层 | crate | 职责 |
|----|-------|------|
| 类型层 | fuyao-api | 纯类型定义（ToolDefinition / ToolEntry / ToolFn / ToolOutput / ToolCallContext）+ handler 侧辅助（tool_handler / parse_args），零业务逻辑 |
| 实现层 | fuyao-tools | 内置工具实现 + 安全防护 + 静态注册表 |
| 编排层 | fuyao-core | 工具执行调度（orchestrate + executor） |

调用链：`fuyao-app::build_tool_registry` 收集工具（内置 + MCP）→ 注入 `Engine::new` → ReAct 循环中 LLM 返回 ToolCalls → `tool_exec` 调度 → session 级执行 → 结果经 dispatch 管道推送。

## 工具定义（ToolDefinition）

发给 LLM 的工具定义遵循 OpenAI Function Calling 规范，三层嵌套：

```text
ToolDefinition              ← type="function"
  └─ ToolSchema             ← name + description + parameters
       └─ ToolParameters    ← type="object" + properties + required
```

参数属性（ToolParameterProperty）支持 type / description / default / enum / items。实现 Serialize + Deserialize（喂 LLM 走 Serialize；MCP 工具的 schema 来自 server 的 JSON，bridge 反序列化成强类型后直接包成 `ToolEntry` 交付，装配层零序列化往返）。

## ToolFn：boxed async closure

```text
ToolFn = Arc<
    dyn Fn(serde_json::Value, ToolCallContext, CancellationToken)
        -> Pin<Box<dyn Future<Output = ToolOutput> + Send>>
    + Send + Sync
>
```

不是 trait，不是裸 fn pointer——是 Arc 包装的 boxed async closure 类型别名。

- **Arc**：handler 被 clone 到并行任务中（多 session 并发 + session 内并行）
- **Pin<Box<dyn Future>>**：统一不同闭包的 Future 类型
- **返回 ToolOutput**：统一结果信封（`Value` JSON 对象 / `Text` 纯文本 / `Err` 错误），wire 序列化（`to_wire`）由信封单点拥有，错误变体恒出 `"error"` 键
- **CancellationToken**：本次工具批次的中断信号，handler 据此优雅收尾（见下文「中断交互」）

工具 handler 统一写规范签名 `async fn(args, ctx, cancel) -> ToolOutput`，注册时经 `tool_handler` 一步包装成 `ToolFn`——`Arc` / `Box::pin` 的类型体操集中在一处，工具站点零样板。

## 工具注册（引擎级共享）

### 引擎级 ToolRegistry（构造时注入）

工具必须在 `Engine::new` 前收集成 `ToolRegistry` 一次性注入。

```text
fuyao-tools/src/registry.rs:
  static TOOL_REGISTRY: LazyLock<HashMap<String, ToolEntry>>
```

首次访问时初始化，进程内单例（内置工具静态表）。每个 category 模块暴露 `register(&mut map)` 注册子工具，经 `insert_tool` 以 schema 名为 key 写入（工具名单一来源，重名 panic 暴露编程错误）。

`fuyao-app::build_tool_registry` 的注册流程：
1. `collect_builtin_tools()` 取全部注册工具（按 `[tools.enabled]` 过滤），`ToolEntry` 是共享类型，clone 即收集
2. `collect_mcp_tools()` 收集 MCP 工具（有配置时 start_all + get_tool_entries 直返 `ToolEntry` 列表）
3. `ToolRegistryBuilder::register_all(...)` 注入
4. `Engine::new(params, providers, tools, plugin_host)` 构造时传入

> **过滤在收集阶段做**：`[tools.enabled]` 过滤在 `collect_builtin_tools` 内部（`is_tool_disabled`），MCP 工具按 server 级配置过滤。注册到 ToolRegistry 的都是最终启用的。
>
> **规则：默认全开。** 未在 `[tools.enabled]` 列出的工具默认启用，只有显式 `false` 才禁用。

### ToolEntry（全系统单一类型）

`ToolEntry`（schema 定义 + 执行 handler + 可见性元数据）定义在 fuyao-api，工具系统各参与方共享同一类型：fuyao-tools 的静态注册表、fuyao-mcp 的 bridge、fuyao-core 的引擎注册表、fuyao-app 的装配全部直接使用，无任何逐字段转换。工具名取 schema 定义里的 `function.name`（`ToolEntry::name`，单一来源），注册经 `insert_tool` 重名即 panic。

### ToolRegistryBuilder

链式构造器：

```text
let mut builder = ToolRegistryBuilder::default();
builder = builder.register_all(builtin_entries);
builder = builder.register_all(mcp_entries);
let registry: ToolRegistry = builder.build();
```

`registry.definitions_json_for(is_child, definition_tools)` 序列化工具定义给 `StreamOptions.tools`（喂给 LLM），序列化时按 session 上下文做 per-session 可见性过滤（见下文「工具可见性」）。

## 工具可见性（per-session 过滤）

工具注册是引擎级共享（一份 `ToolRegistry`），但**发给 LLM 的 schema** 是 per-session 的——不同 session 用不同 Agent 定义、不同工具集。可见性过滤发生在序列化 schema 时（`resolve_model` → `definitions_json_for`），不修改引擎级注册表。

### 三层过滤叠加（交集语义）

```text
引擎级注册漏斗（一次性，所有 session 共享）：
  [tools.enabled] 显式 false 的工具根本不进 ToolRegistry
        │
        ▼  per-session schema 序列化时再收窄：
  ┌─────────────┴─────────────┐
  │ is_child：子 session 隐藏 child_invisible 工具（递归防护） │
  │ definition_tools：定义层显式 false 的工具隐藏（最小权限）   │
  └─────────────┬─────────────┘
        ▼
  发给 LLM 的 schema 子集 = 全局 ∩ 非 child_invisible ∩ 定义层允许
```

| 过滤层 | 来源 | 作用域 | 语义 |
|--------|------|--------|------|
| 全局 `[tools.enabled]` | fuyao.toml | 引擎级（注册漏斗） | 显式 `false` 不进注册表；最高优先级硬约束 |
| `child_invisible` | `ToolEntry` 字段 | per-session（子 session） | 子 session 看不到派生类工具（如 `subagent`），阻断嵌套派生 |
| 定义层 `tools` | `agents/{name}.md` frontmatter | per-session（按所选定义） | 与全局同款 `key=bool`，未列出默认启用，显式 `false` 收窄 |

全局禁用是最高优先级——定义层即便声明某工具启用，全局已禁用则该 session 仍无此工具。定义层只能在全局允许范围内**加限制**，不能放开。

### 执行点：schema 唯一，派发不二次过滤

可见性过滤**只在 schema 序列化处**（`definitions_json_for`）生效——LLM 看不到的工具就不会调用，从机制上阻断。派发查表（`execute_single` 的 `registry.get`）**不做二次过滤**，与 `child_invisible` 的既有惯例一致：若 LLM 幻觉调用了 schema 里没有的工具，`registry.get` 仍能查到 handler，但这一路径几乎不触发；即便触发，未知工具容错会返回明确提示，让 LLM 自行决策。

### 定义层 tools 的数据来源：SessionCtx 持有完整 AgentDefinition

```text
create_session / create_child / resume / fork
   │  resolve_definition(agent_paths, agent_config, usage) → Result<AgentDefinition, PromptError>
   │  加载一次（含 mode 校验，未知名 / mode 不符报错），创建时定死
   ▼
SessionCtx.definition: AgentDefinition   ← per-session 持有，整 session 不可变
   │  .tools 供 resolve_model 序列化 schema 时读取
   │  .system_prompt 供 build_system_prompt 复用（同一份 definition，零重复加载）
```

工具集改变会冲掉 LLM 前缀缓存，故 `definition` 创建时定死、整 session 不可变（与 `agent_config` 红线一致）。持有完整 `AgentDefinition` 而非只存 `tools` 切片——后续定义字段扩展（权限、资源限制等）可直接复用此容器。

### 未知名处理：静默忽略 + WARN

全局 `[tools.enabled]` 与定义层 `tools` 对**未知工具名**（拼错 / 已卸载）的处理完全统一：不阻断、不报错，引擎照常运行，仅留 WARN 日志（`tool_name` / `layer` 字段区分来源）。用户的配置错误由用户承担，引擎只留痕不强求。两层共用同一对账函数，逻辑一致不漂移。

## 安全防护（纵深防御）

### 路径安全（check_sensitive_path）

五层检查依次短路：

| 层 | 规则 |
|----|------|
| 1 | `FUYAO_WRITE_SAFE_ROOT` 白名单（环境变量设置时生效） |
| 2 | 敏感路径前缀（`/etc/` `/boot/` `/sys/` `/proc/` `/dev/` `C:\Windows\` 等） |
| 3 | 敏感系统文件（`/etc/passwd` `/etc/shadow` `/etc/sudoers` `sshd_config` 等） |
| 4 | 用户主目录敏感文件（`~/.ssh/id_rsa` `~/.bashrc` `~/.gitconfig` `~/.npmrc` 等） |
| 5 | 特殊文件名（`.env` `.htpasswd` `authorized_keys`，任意位置） |

配套防护函数：

| 函数 | 防什么 | 用在哪 |
|------|--------|--------|
| `is_internal_path` | 框架内部路径（`.fuyao/.env`），防 prompt injection | read 工具 |
| `has_binary_extension` | 31 种二进制扩展名（`.exe .png .pdf .zip .db .so` 等） | read 工具 |
| `is_blocked_device` | 设备文件（`/dev/zero /dev/random /dev/tty` 等 12 个 + `/proc/self/fd/*`） | read 工具 |

### 命令安全（check_command_safety）

两级阻断：

| 级别 | 模式 | 示例 |
|------|------|------|
| critical | 确定性高危 | `rm -rf`、`dd of=/dev/sd*`、`mkfs.*`、fork 炸弹 |
| medium | 系统级风险 | `curl|sh`、`shutdown`、停关键服务 |

> **设计哲学**：不做完整 Guard，只拦确定性高危。其余放行让 Agent 自主决策。

配套：`validate_workdir`（白名单字符校验，挡 shell 注入）、`build_safe_env`（屏蔽 API key 环境变量，防泄漏）。

### 脱敏（redact_sensitive_text）

七组正则（fancy_regex）：API key 前缀 / 环境变量赋值 / JSON 字段 / Auth header / 私钥块 / 数据库连接串 / JWT。

应用点：read / grep / bash 输出，防止泄漏。

### 文件追踪（去重 + 外部编辑检测）

read / write / edit 工具共享一套文件追踪器（基于 mtime 时间戳）：

| 机制 | 用在 | 行为 |
|------|------|------|
| **去重检测** | read | 已读且未修改的文件再次读取时提示"内容未变"，避免 LLM 浪费轮次 |
| **外部编辑检测** | write / edit | 写入前比对 mtime，若文件自上次跟踪后被外部修改，返回 warning（不阻断）——防止覆盖用户的手动改动 |

> 这是"建议而非阻止"的设计——工具仍执行操作，但让 LLM 知道潜在风险。

## 工具执行编排（tool_exec）

`execute_tools` 入口负责智能并行 / 串行判定，session 级执行：

```text
LLM 返回 ToolCalls
    │
    ▼
读 [tools.runner] 配置
    │
    ▼
should_parallelize? ─── 整批二选一判定（见下）
    │
    ├── 是 → execute_parallel（Semaphore 限流 + JoinSet 管理）
    └── 否 → execute_sequential（逐个 await）
    │
    ▼
每个工具：execute_single
    │  registry.get(name) → 未找到返回错误信封 {"error": "未知工具: xxx"}
    │  JSON 反序列化 args → 失败回退 Null
    │  构造 ToolCallContext → handler(args, ctx, cancel).await → to_wire() 序列化
    │
    ▼
结果经 dispatch 管道推送 OutputEvent::ToolResult
    │  完成一个 emit 一个（中断不丢已完成结果）
    │
    ▼
continue ReAct 循环（工具结果回喂 LLM）
```

### 整批二选一调度策略

`execute_tools` 读 `[tools.runner]` 配置，调 `should_parallelize` 对整批一次性判定：能并行走 `execute_parallel`，否则走 `execute_sequential`。**不**做批次内拆分（这几个并行、那几个串行）。判定是木桶效应——批里有一个工具不安全，整批串行。

### 并行 / 串行判定（should_parallelize）

四步短路：

| 步 | 条件 | 结果 |
|----|------|------|
| 1 | 工具数 ≤ 1 | 串行 |
| 2 | 任一工具在 `never_parallel` | 串行 |
| 3 | `path_scoped` 工具的路径重叠 | 串行（路径冲突） |
| 4 | 非 path_scoped 工具在 `parallel_safe` | 并行 |

默认：`never_parallel = ["bash", "todowrite"]`、`parallel_safe = ["read", "glob", "grep", "skill", "webfetch", "subagent"]`、`path_scoped = ["read", "write", "edit"]`。

> 注：`read` 同时在 `path_scoped` 和 `parallel_safe`，`should_parallelize` 里 `path_scoped` 检查优先（先查路径重叠），通过后 `continue` 跳过白名单检查。

### 并行执行设计（execute_parallel）

```text
Semaphore(max_concurrent=8)  ← 限同批并发，函数局部对象（非全局状态）
JoinSet<(idx, ToolExecResult)>

for (idx, tc) in tool_calls:
    spawn task:
        acquire Semaphore 许可
        execute_single(tc) → (idx, result)

while join_next():           ← 逐个收，哪个先完成收哪个
    emitter.emit(ToolResult) ← 完成一个 emit 一个
    slots[idx] = result      ← 按 idx 写预分配槽位

slots.flatten()              ← 恢复提交序返回
```

**两个顺序设计**：

- **emit 顺序 = 完成顺序**：`JoinSet::join_next` 哪个先完成先发哪个事件，UI 先看到先完成的工具结果（UX 友好）
- **返回顺序 = 提交顺序**：用 `(idx, result)` + 预分配 `Vec<Option>` 槽位，最后 flatten 恢复提交序，喂 LLM 时 tool_result 与 tool_call 顺序对齐（确定性）

### 路径重叠检测（3 步纯逻辑）

- `extract_path_from_args`：取 `args.path` 字符串 → `~` 展开 → 相对路径补 cwd → 规范化
- `canonicalize_path`：不要求文件存在，消除 `.`/`..`（逐 component 遍历，`..` 弹栈）
- `paths_overlap`：按 component 前缀比对，一个是另一个的前缀（父子/同目录）即重叠

### 中断交互（双保险取消）

工具执行段的取消是**双保险**模型，两条路径并存：

```text
① 显式 CancellationToken（软通知，主动）
   turn.rs 派生 child_token（session shutdown_token 的子节点）传入 execute_tools
   → handler 拿到 token，长任务在 select! 监听 cancelled()
   → 命中后优雅收尾（terminal 杀进程组 + forget）→ 返回取消标记

② 外部 drop（硬杀，被动兜底）
   select! 命中中断 / shutdown → exec_fut 被 drop → JoinSet drop → tokio abort 未完成任务
   → 不监听 token 的短任务靠此兜底，局部资源由 tokio 回收
```

**token 派生层级**：child_token 是 session shutdown_token 的子节点——shutdown 时 parent→child 自动传播；interrupt 命中时 turn.rs 显式 cancel child_token。两者汇入同一 `cancelled()`，handler 不需区分为什么被取消。工具内部不能反向 cancel 整个 session（避免越权）。

**已完成结果不丢**：工具结果「完成一个落一个库」（handler 返回 → result_tx → turn.rs 立即 `insert_message` 落 DB）。中断时 `try_recv` 清空 channel 把已完成但未收的也落库，再为未完成的统一补发中断式 ToolResult（查 DB 已 answered 集合跳过，不重复）。串行 / 并行走同一 channel、同一 select!，取消行为完全一致。

**无宽限期**：turn.rs 中断分支 cancel child_token 后立即走清空 + 补发，不等 handler。清理动作（杀子进程）是 tokio task 内部逻辑，token cancel 后继续推进，不需要 turn.rs 等——中断响应与纯 drop 一样快。

### 两层并发正交、互不冲突

- **session 间并发**：每 session 一个 tokio task，互不等（异步并发）
- **session 内工具并行**：单 task 内用 JoinSet 把一批 tool_calls 并发跑
- **零协调合规**：`Semaphore`/`JoinSet` 都是 `execute_parallel` **每次调用的局部对象**（非 Engine 字段、非全局静态），调用结束即销毁。session A 的限流管不到 session B——多个 session 同时各自并行调工具叠加起来，引擎依然零跨 session 协调。

## 关键设计决策

### 为什么类型 / 实现 / 编排三层分离？

类型层零逻辑（fuyao-api 纯定义），实现层不知道何时被调用（fuyao-tools），编排层不知道工具内部细节（fuyao-core）。三者正交，可独立测试，替换一层不影响其他。

### 为什么 ToolFn 用 boxed closure 而非 trait？

trait object 需要定义 trait + impl，每个工具都要写样板。规范签名的 async fn 经 `tool_handler` 一步包装成 boxed closure，`Arc` / `Box::pin` 的类型体操集中一处，工具站点零样板。Arc 确保跨任务 clone 廉价。

### 为什么未注册工具不 panic？

返回错误信封 `{"error": "未知工具: xxx"}` 让 LLM 自己决策（可能是模型幻觉了不存在的工具）。符合"自主决策"原则——错误信息含明确建议，避免卡死。

### 为什么 bash 在 never_parallel？

bash 有副作用（文件修改、网络请求），并行执行可能导致竞态。todowrite 是覆盖写，并行会互相覆盖。只读工具（read / glob / grep）可安全并行。

### 为什么整批二选一而非混合调度？

路径冲突是跨工具的、LLM tool_call 的隐含顺序依赖引擎无法判定，保守做法保证正确。实际 LLM 想并行时通常一批都是只读操作，`should_parallelize` 直接判定并行——混合调度的复杂度换不来多少收益。

### 为什么 emit 顺序用完成序、返回顺序用提交序？

- **emit 完成序**：UX 友好，UI 先看到先完成的工具结果，不必等最慢的那个
- **返回提交序**：喂 LLM 时 tool_result 与 tool_call 顺序对齐，确定性（OpenAI 协议要求配对）。用 `(idx, result)` + 预分配 `Vec<Option>` 槽位 O(n) 恢复，无需排序。

### 为什么 Semaphore / JoinSet 是函数局部对象？

跨 session 零协调的落实——如果 Semaphore 是 Engine 字段，session A 的限流会管到 session B。函数局部对象每次 `execute_parallel` 调用新建，调用结束即销毁，A 的限流完全管不到 B。多个 session 同时各自并行调工具叠加起来，引擎全程零跨 session 协调。

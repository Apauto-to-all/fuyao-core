# 引擎内核设计

> 本文解释 fuyao-core 引擎内核的设计决策与代码组织：两层分离、单一入口/出口、ReAct 循环、双队列、中断机制、重试、shutdown 等。API 签名见 `cargo doc --workspace`；架构全局见 [核心架构](核心架构.md)。

## 设计目标

引擎内核负责两件事，分别属于"能力共享层"和"对话执行层"：

1. **能力共享层（Engine）** — 启动一次，装配 provider / DB / 工具 / 插件工厂；管理多对话生命周期；单一入口接收（`send`），出站走 per-session 通道（fan-in 由 `fuyao-app::App` 承担）
2. **对话执行层（session task）** — 每个 session 一个独立 tokio task，跑 ReAct 循环（双队列 + 中断 + 重试 + 工具调用）

不做：工具实现（`fuyao-tools` 负责）、提示词构建（`fuyao-prompt` 负责）、压缩算法实现（`fuyao-session/compressor` 负责）。这些通过依赖注入或函数调用协作。

> **`fuyao-core` 依赖 `fuyao-session`**：引擎内核直接持 `SessionStore` 共享 DB 句柄给所有 session（事件级落库的统一写入入口）。

## 两层分离架构

### Engine（能力共享层）

```text
Engine 持有：
  · store: Arc<SessionStore>         数据库（事件级落库的统一写入入口）
  · providers: Arc<ProviderRegistry> 多 Provider 路由
  · tools: Arc<ToolRegistry>         工具注册表（所有 session 共享）
  · plugin_host: Arc<PluginHost>     插件工厂集合（每 session 生成独立实例）
  · sessions: Mutex<HashMap>         session_id → SessionHandle 调度表
  · params: EngineParams             引擎级配置（agent_paths）
  · shutdown: Arc<AtomicBool>        同步快路径 flag（send 立即拒绝）
  · shutdown_token: CancellationToken 引擎级取消信号
```

> **出站通道是 per-session 的**——每个 session 在 `assemble_session` 时建一条无界 `tx_event / rx_event`，`tx_event` 存进 `SessionHandle`，`rx_event` 返调用方。`Engine` 本身不持全局出口；`rx_event` 的 fan-in 汇聚由 `fuyao-app::App`（装配层）承担，`App::recv` 是对外单一出口。子任务 session 的 rx 不进 fan_out，由派生方独占消费。

### Session task（对话执行层）

每个 session 一个 tokio task，`run_session` 主循环内跑 ReAct：

```text
SessionHandle 持有：
  · guide / pending 双队列（SharedQueue = Arc<Mutex<VecDeque<InboundUser>>>）
   · tx_inbound / tx_interrupt / tx_plugin + 控制通道（四条通道，Engine::send 路由进来）
  · tx_event（该 session 的出站发送端，rx_event 已返调用方）
  · shutdown_token（child_token，派生自引擎级 root）
  · task: JoinHandle（session task 句柄）
```

## 交互动作

详见 [核心架构](核心架构.md) 的"交互动作"一节。本节只补关键实现细节：

### send 的四通道分流

```text
engine.send(id, event):
   ├── InputEvent::User     → 字段照搬转化 output UserMessage → tx_inbound
   ├── InputEvent::Interrupt → tx_interrupt（独立通道，select! 中断点直接监听）
   ├── InputEvent::Plugin   → tx_plugin（由 session task 过 dispatch 管道发外部）
   └── InputEvent::Compress → 控制通道（turn 边界消费，跳过阈值 / 反抖动，复用压缩执行流程）
```

#### 四类消费语义

四条通道按「何时消费、如何消费」分四类语义，通道数封顶在语义类数——后续每拓展一个功能，先判它属哪类，进对应通道，不随功能膨胀：

| 类 | 语义 | 消费时机 | 归属通道 |
|----|------|---------|---------|
| A | 驱动 turn 的内容 | 循环顶，入队跑 ReAct | 入站通道（User） |
| B | 命令主循环做事 | 循环顶（turn 边界），不入队，直接作用于 session | 控制通道（Compress） |
| C | 抢占在途工作 | select! 与 LLM 流竞速，可打断在途 turn | 中断通道（Interrupt） |
| D | 独立转发通知 | 任何时候，不碰 session 状态 | Plugin 通道（Plugin） |

B 类是新引入的语义：通道载荷是一个「命令」集合，每个命令代表一种「让主循环做事」的信号。手动压缩是它的第一个命令；后续的清空上下文、强制重提示等同类信号均作为新命令加入同一条控制通道——主循环的 `select!` 只需一个消费臂，臂数恒定。B 类只在 turn 边界消费，不与 LLM 流竞速、不抢占在途 turn（等当前 turn 跑完再处理）；同类命令之间靠主循环 task 串行消费天然有序。引擎对 B 类命令**忠实执行**：收到几条就跑几次，不做同批次去重 / 合并 / 冷却——那属于上层职责，引擎不替外部解释意图。C 类（中断）在 `select!` 中 biased 优先，抢占一切——这是它独占的语义。

User 分支不再直接操作 guide/pending 队列，而是经入站通道 `tx_inbound` 送进 session task，由 `handle_inbound_user` **纯入队**（零 side effect）。拦截/push/发送三时机统一在 `inject_messages` 消费时刻过 `emit_to_history`，与 assistant / tool_result 完全对称。

### 出站事件流（per-session + fan-in）

出站通道 per-session 化后，事件的 shutdown / 退出语义如下：

```text
session task 产出事件 → tx_event.send（落库后才入 channel，不反压 ReAct）
   │
   ▼
rx_event（调用方持有）
   ├── session task 退出（end_session / shutdown）→ tx_event drop → rx_event.recv() 返 None
   └── 调用方据此优雅退出消费循环
```

`App` 装配层为每个主 session spawn forwarder 把 `rx_event` 转 `fan_out`，`App::recv` 在 `fan_out` 上消费——所有 forwarder 退出 + `App` drop `fan_out_tx` 后，`App::recv` 返 None。shutdown 后**不丢** shutdown 前的最后几条事件：session task 先落库再 emit，forwarder 把残余事件转完后才退，消费者收完完整事件流后优雅退出。

## 统一消息处理管道（dispatch）

详见 [核心架构](核心架构.md) 的"统一消息处理管道"一节。本节补关键实现：

```text
dispatch 管道四段（session 级）：
  拦截（intercept） → lock hooks + hook_output_intercept
  处理（process）   → ProcessFn 回调（入队/收集批次/投递信号），耗时动作（工具执行）在管道外
  发送（deliver）   → Emitter::emit（盖 session_id + tx.send）+ hook_output_observe
  观察（observe）   → 已含在 deliver 内（串行，发送在前、观察在后）
```

`dispatch_intercept` 是 `dispatch` 的子集（仅拦截），返回拦截后的 `Option<OutputEvent>`——工具调用回灌时用：逐个 tool_call 拦截，Block 的跳过，未 Block 的累积成 effective_tool_calls，作为存储/发送/执行三者的唯一数据源。

`emit_to_history` 是**进历史消息的统一入口**：拦截 → 用拦截后事件构造 Message 经 `store.insert_message` 单条落 DB → 自动累积 `session.total_*`（assistant 角色）→ 发送事件 → 观察。保证"拦截 → 存储 → 消费"三者数据一致。

## ReAct 循环（run_turn）

每轮 ReAct 的完整流程：

```text
run_pre_turn_compression（pre-turn 主动触发压缩，详见会话系统设计）
   ↓
inject_messages（消费 guide/pending 队列，过 emit_to_history 把消息注入历史）
   ↓
build_chat_request（凑历史 + 工具定义 + 配对兜底）
   ↓
resolve_model（拆 model_id + 整束取思考参数；None 回退 [models.default]，没配 fail-loud 发 Error）
   ↓
materialize_resolved（写回物化：resolved 真值落 model_config + 共享 session_params）
   ↓
run_stream_with_retry（react 层重试驱动，内部调 stream::run_stream_session）
   │  每个 chunk → dispatch(Chunk) 经管道发外部
   │  同时累积 TurnState（text / reasoning / tool_calls）
   ▼
两段 select!（流式期间 + 工具执行期间）：
   biased 优先 shutdown 分支 → 发 Interrupt(Shutdown) + 中断落库退出
   interrupt 分支 → 发 Interrupt(source) + 中断补发 ToolResult
   主分支 → 流完成 / 工具完成继续
   ↓
判断 finish_reason
   ├── Stop ──► handle_final_reply：发 Assistant + accumulate_usage_and_cost
   │             + maybe_spawn_title_generation（首轮后异步生成标题）
   │             + persist（store.update 落 session 元数据）
   │
   └── ToolCalls
         │  逐个 dispatch_intercept 拦截 tool_calls → effective_tool_calls（Block 的跳过）
         │  用 effective 构造 AssistantMessage（存/发/执行三者一致）
         │  execute_tools 批量执行（智能调度：整批并行或串行，完成一个 emit 一个）
         │  完成的 ToolResult 回流进管道（emit_to_history）
         │  回到 run_turn 顶部（ReAct 循环继续）
```

## 双队列（guide + pending）

两个对等的 `Arc<Mutex<VecDeque<InboundUser>>>`（`SharedQueue`），加 `Notify` 唤醒。

- **guide 队列**：高优先级消息，触发 ReAct 循环时立即投递
- **pending 队列**：普通消息，等 AI 不再调用工具（finish_reason=stop）后才投递

### 消费时机（三个解禁点）

| 时机 | 位置 | 行为 |
|------|------|------|
| ① 一批工具全完成后 | `handle_tool_calls` 内 | 只看 guide（链在进行，pending 不动），全取注入 |
| ② 最终回复后 | `handle_final_reply` 内 | 固定顺序：pending 全倒 guide → guide 全取注入（pending 优先于 guide） |
| ③ task 空闲时 | `run_session` 主循环 | guide 空时先 `drain_pending_to_guide` 再判空（task 空闲 = 无进行中的链 = pending 解禁） |

> 时机 ③ 是补丁——修复原 main 循环只看 guide 致 task 空闲时只发 pending 永远进不了 turn 的死信 bug。

## 中断机制（interrupt）

中断按当前执行阶段分类，三段 select! 捕获：

| 中断点 | 文件位置 | 场景 |
|--------|---------|------|
| 流式期间 | `turn.rs` 中断点① | LLM 正在流式输出 |
| 工具执行期间 | `turn.rs` 中断点② | 工具正在执行 |
| 空闲等待 | `run_session` idle select! | 等待队列消息时 |

`TurnState`（`Arc<Mutex>` 共享给 stream 写、中断分支读）在流式过程中持续累积已接收的 chunk，中断时读取部分结果生成中断 ToolResult。

`classify()` 集中判断中断场景（`Streaming` / `StreamingWithToolCalls` 等）。

### shutdown 也是中断

shutdown 复用现有中断链路——把它当作"特殊的 interrupt"：

- 两段 select! 都加 `biased` 优先的 shutdown 分支（高于 interrupt）
- shutdown 分支发 `Interrupt(Shutdown)` + 走相同的中断落库退出路径
- retry 退避 sleep 用 `tokio::select!` 监听 `shutdown_token.cancelled()`，收到立即返回 `Err(StreamError::Cancelled)` 冒泡给 turn.rs

这让 shutdown 时正在跑 turn 的 session 立即优雅退出，不依赖 10s 超时 abort 兜底。

## 重试机制（RetryRunner）

LLM 调用遇可恢复错误（RateLimit / Timeout / Connection / 5xx）自动重试，每次重试前发 `OutputEvent::Retry` 给 UI（含 attempt / wait_ms / cause）。

**关键设计**：

| 决策 | 选择 | 理由 |
|------|------|------|
| 重试代码位置 | react 层（`retry.rs::run_stream_with_retry`），不在 provider 层 | per-session 发 Retry 事件需要 session_id；全局装饰器拿不到 |
| 重试与中断的关系 | 完全正交（retry 不感知 interrupt） | sleep 期间外层 select! drop future 自然取消；不需要 phase/Backoff 字段污染 interrupt 模块 |
| 首 chunk 边界 | state 持 text/reasoning 非空即视为已吐首 chunk | 避免重试让 UI 看到重复输出（已吐内容难以撤销） |
| max_retries 默认值 | `u32::MAX`（无限重试） | 可恢复错误说明供应商侧短时不可用，引擎应持续重试直到恢复 |
| stream 模块职责 | 移除"发 Error 事件"（错误冒泡） | stream 只做流式解码，发什么事件由调用方决定（retry 发 Retry，turn.rs 发 Error） |
| 退避算法 | 复用 `fuyao_provider::backoff_duration` | 指数退避 + retry-after 头 + 双封顶 |
| 日志级别 | WARN（不报警） | 重试属可恢复，按"半夜叫醒测试"不应触发报警 |

## 工具执行（tool_exec）

`execute_tools` 入口负责智能并行 / 串行判定（详见 [工具系统设计](工具系统设计.md)）：

```text
读 [tools.runner] 配置 → should_parallelize 整批判定
   ├── 是 → execute_parallel（Semaphore 限流 + JoinSet 管理，完成一个 emit 一个）
   └── 否 → execute_sequential（逐个 await）
```

**两个顺序设计**：

- **emit 顺序 = 完成顺序**：`JoinSet::join_next` 哪个先完成先发哪个事件
- **返回顺序 = 提交顺序**：用 `(idx, result)` + 预分配 `Vec<Option>` 槽位，最后 flatten 恢复提交序喂 LLM

**中断交互**：中断时 select! drop `exec_fut` → JoinSet 被 drop → tokio 自动 abort 所有未完成任务。已完成的已 emit；中断分支对全部 tool_calls 统一补发中断式 ToolResult（content 格式 `[{source}][{reason}]`）。

## 安全边界

引擎内核有几处**未设硬上限**的执行路径，目前依赖外部机制兜底：

| 路径 | 缺失的上限 | 当前兜底 |
|------|-----------|---------|
| ReAct 循环 | 无 `max_turns`（轮次计数器） | LoopGuard 的 Abort（interrupt_count ≥ 3）+ 用户 cancel + Engine::shutdown |
| LLM 重试 | 无 `max_retries` 次数硬限（默认 `u32::MAX`） | 用户可在 `[llm.retry]` 配小 |
| 工具执行 | 无单工具超时 | 工具内部超时（bash 120s / webfetch 30s / grep 60s） |

> 若 LoopGuard 未加载 + 重试配的是无限，理论上可无限循环 / 无限重试 / 工具 hang 住只能靠外部 Interrupt 或 shutdown。

## 关键设计决策

### 为什么两层分离（Engine + Session task）？

能力共享与对话状态生命周期完全不同：

- **能力**（DB / Provider / 工具 / 插件工厂）：启动时装配一次，引擎持有，所有 session 共享
- **对话状态**（队列 / ReAct 循环 / 双队列）：按需创建，各 session 独立，互不等

混在一起，要么引擎级状态被对话污染，要么对话状态没地方放。分两层后，引擎装配完即可服务任意数量对话，多 session 并发天然支持。

### 为什么单一入口 + fan-in 单一出口？

**单一入口**让所有对话级事件从一个口进——调用方不用维护"哪个对话用哪个入口"的映射；**单一出口**（`App::recv`）让所有主 session 的产出从一处流出——消费者按 session_id 归类即可。出站通道本身是 per-session 的（不让 emit 反压 ReAct），装配层 `App` 用 forwarder 把多路 rx 汇聚成单一 fan_out，重建「单一出口」语义。多 session 并发的复杂度被降维成"按编号路由"+"每 session 独立装配"两件简单事。

### 为什么 session id 全程标签？

事件一产生就盖 session_id（不是跨边界时才打），消费者拿任意一条事件都能取到 `session_id` 分流，无需匹配。这是多对话并发不串的底线。

### 为什么 Agent 配置不可变（创建时定死）？

前缀缓存红线：Agent 配置改了会冲掉 LLM 的前缀缓存，每次请求重新计算全量。冻结后，整个会话复用同一前缀缓存，大幅降低延迟和成本。

### 为什么 model 配置是对话级且可运行时切？

model 配置整 session 共享一份（`SessionParams.model_config`），不同对话用不同模型；要切模型调 `Engine::update_session_params` 写回，下一轮自然用新模型。前缀缓存红线只锁 `agent_config`（改 system_prompt 才冲前缀缓存），切模型不改 system_prompt，故 `model_config` 允许运行时 update。这样多 session 并发时，不同对话有不同人格（agent_config 创建时定死）、不同模型（model_config 可切），互不干扰。

### 为什么 resolve_model 后要写回物化（materialize_resolved）？

兜底解析（`model_id = None` 走 `[models.default]`）若现取现用不回写，靠 default 跑的会话会出现真值丢失：DB 的 assistant 消息 `model_id` 落 NULL、费用计算读不到 model_id 漏算、标题生成回退时同样读不到 model_id 而跳过。`materialize_resolved` 在解析成功后把 resolved 的整束（model_id + thinking_type + reasoning_effort）写回 session 的 local 副本与共享 `session_params`，让下游三处消费点读到实际生效值。

写回规则与解析同序，以 model_id 为锚：`model_id = None`（走了兜底）才整束覆盖，`model_id = Some`（用户显式指定）则全不动。写共享态前加锁复检 `model_id.is_none()`，并发 `update_session_params` 已把 model_id 设 Some 则跳过——用户运行时切模型的意志优先。

### 为什么中断用独立通道（tx_interrupt）而非共享标志？

中断需要实时送达正在 await 的 task。用独立 mpsc 通道，`run_turn` 在关键 await 点 `select!` 同时监听 LLM 流和中断通道——中断到达时立即响应，无需轮询标志，零延迟。队列用 Notify 唤醒（不混通道），两条机制正交。

### 为什么工具结果不走队列？

工具结果是 ReAct 循环内部状态（产生它的 task 正握着控制权，无并发），与外部异步到达的用户消息根本不同。塞进队列再立刻取出来，队列里永远只躺着刚塞的那一条，这队列没有存在意义。**外部消息走通道（唯一入口），内部状态走 task 本地内存**——两条边界干净利落，不串。

### 为什么 plugin 用「工厂 + 实例」两层模型？

多 session 并发时若插件状态共享，session A 的循环计数会影响 session B（串台）。工厂模板引擎级共享（无 per-session 状态），每 session 调 `create_instance` 生成独立实例（持独立 state），多 session 并发互不串台。

### 为什么重试在 react 层而不在 provider 层？

发 `OutputEvent::Retry` 需要 session_id 标签（事件全程标签原则）。provider 层的全局装饰器拿不到 session_id——曾尝试过 `RetryingProvider` 装饰器方案，因拿不到 session_id 发不了 per-session 事件而推翻。架构选型必须从「事件流」倒推，不能只看代码侵入度。

### 为什么 dispatch 分 intercept 和完整管道？

工具调用需要"拦截回灌"——逐个 tool_call 拦截后累积成 effective_tool_calls 作为下游唯一数据源（存储/发送/执行三者一致）。`dispatch_intercept` 只做拦截返回结果，调用方据此构造最终消息再决定怎么 deliver。

### 为什么工具调用要捕获拦截结果？

引擎是消息驱动的——拦截后的消息才是"最终消息"。逐个 `dispatch_intercept` 拦截 tool_call，累积 effective_tool_calls 作为三个下游的统一数据源：

1. **CLI 显示**（发 ToolCall 事件）
2. **会话存储**（AssistantMessage 中的 tool_calls）
3. **工具执行**（execute_tools 用最终参数调用）

若用 fire-and-forget 的 `dispatch`，拦截修改只影响显示，执行和存储仍用 LLM 原始参数——三者不一致：插件把 `git` 改成 `rtk git`，但实际执行和数据库里存的还是 `git`。被 Block 的工具调用直接跳过（不执行、不存储），但**配对兜底**在 `build_chat_request` 序列化层补一条 error tool_result（OpenAI 协议硬约束在这里满足，不归拦截层管）。

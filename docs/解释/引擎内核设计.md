# 引擎内核设计

> 本文解释 fuyao-core 引擎内核的设计决策与代码组织。API 签名见 `cargo doc --workspace`；架构全局见 [核心架构](核心架构.md)。

## 设计目标

引擎内核只做三件事：

1. **消息驱动** — 接收输入，分发处理
2. **ReAct 循环** — 驱动 LLM 思考 + 工具调用的循环
3. **中断响应** — 实时取消正在执行的操作

不做：会话持久化（`SessionPlugin` 负责）、工具实现（`fuyao-tools` 负责）、提示词构建（`fuyao-prompt` 负责）。这些经 Hooks / Plugin 注入，引擎内核零感知。

> **这正是 `fuyao-core` 不依赖 `fuyao-session` / `fuyao-tools` 的原因**——它们是可插拔能力，不是引擎硬依赖。

## 双并发 Actor 架构

引擎由两个常驻 tokio 任务组成，通过通道通信：

```text
┌──────────────────────────┐           ┌──────────────────────────────┐
│  Engine                  │  命令通道   │  TurnExecutor                │
│  (InputDispatcher)       │ ────────►  │  (ReAct 循环)                 │
│                          │            │                              │
│  持有：                   │  队列通知   │  持有：                       │
│  · 输入通道接收端          │ ◄────────  │  · provider / agent_ctx      │
│  · 命令通道发送端          │            │  · tools（SharedTools）       │
│  · EventEmitter          │            │  · 命令通道接收端              │
│  · 双队列（guide+pending） │            │  · 双队列（guide+pending）     │
│  · TurnExecutor 句柄      │            │                              │
└──────────────────────────┘           └──────────────────────────────┘
```

**Engine（InputDispatcher）** 负责接收所有外部输入，拦截后入队，通知 TurnExecutor。

**TurnExecutor** 负责从队列取消息，驱动 ReAct 循环（LLM 思考 → 工具调用 → 循环）。

### Engine 主循环

按 `InputEvent` 变体分支：

| 输入 | Engine 处理 |
|------|------------|
| `User` | `dispatch_intercept`（拦截钩子）→ 入 guide / pending 队列 → notify TurnExecutor |
| `Interrupt` | `dispatch`（中断处理）→ 发 `TurnCommand::Interrupt` |
| `Plugin` | `dispatch` → `emit(OutputEvent::Plugin)` |
| `Shutdown` | 发 `TurnCommand::Stop` → 退出主循环 |

### TurnExecutor 队列主循环

```text
loop {
    // 顶部 pending 全部转移到 guide（优先处理）
    取 guide 队列消息 → run_turn() → 完成后取下一条
    空队列时 select! {
        notify → 有新消息，继续取
        命令   → 处理 Interrupt / Stop
    }
}
```

## 消息分发管道（dispatch）

```text
InputEvent
    │
    ▼
┌─ 拦截钩子（intercept）─┐  可修改 / 取消（InterceptResult::Block 短路）
└────────┬───────────────┘
         ▼
┌─ 处理（process）───────┐  构建 / 转换事件
└────────┬───────────────┘
         ▼
┌─ 发送（deliver）───────┐  emit OutputEvent 经 EventEmitter
└────────┬───────────────┘
         ▼
┌─ 观察钩子（observe）───┐  只读副作用（持久化 / 日志）
└────────────────────────┘
```

`dispatch_intercept` 是 `dispatch` 的子集（仅拦截 + 处理，不 deliver）——返回拦截后的 `Option<OutputEvent>`，调用方拿到最终消息后自行 `deliver`。两个用途：

- **用户消息延迟 deliver**：拦截后入队，等 TurnExecutor 取出才走完整管道
- **工具调用捕获**：`stream_session` 对每个工具调用用 `dispatch_intercept` 捕获插件修改后的"最终消息"，供执行与存储消费（详见 [消息驱动一致性](#为什么工具调用要捕获拦截结果)）

## ReAct 循环（run_turn）

每轮 ReAct 的完整流程：

```text
发 OutputEvent(TurnStart)
    │
    ▼
prepare_request（组装 ChatRequest：系统提示词 + 会话历史 + 工具定义）
    │
    ▼
before_llm 拦截钩子（可注入消息 / skip_tools）
    │
    ▼
stream_session（调 Provider::stream_chat）
    │  每个 chunk → OutputEvent(Chunk)
    │  同时 accumulate 到 StreamAccumulator
    ▼
关键 await 点 select! {
    流完成 → 继续
    Interrupt 命令 → 调 interrupt handler → 生成中断 ToolResult
}
    │
    ▼
判断 FinishReason
    │
    ├── Stop ──► output 拦截 + 观察钩子 ──► 本轮结束
    │
    └── ToolCalls
         │
         │  逐个经 dispatch_intercept 拦截 → 捕获"最终消息"
         │  插件可修改参数或 Block 跳过
         │
         ├─► deliver（OutputEvent(ToolCall) 最终版 → CLI + 观察）
         │
         ├─► emit_assistant_message（最终 tool_calls → 存储）
         │
         ├─► tool_runner::orchestrate（用最终参数执行）
         │
         ├─► OutputEvent(ToolResult) → output 钩子
         │
         └─► 回到 prepare_request（ReAct 循环继续）
```

## 工具执行编排（tool_runner）

`orchestrate` 入口负责智能并行 / 串行判定：

| 判定步骤 | 条件 | 结果 |
|---------|------|------|
| 1 | 工具名在 `never_parallel` 列表 | 强制串行 |
| 2 | 工具名在 `path_scoped` 列表 + 路径重叠 | 串行（路径冲突） |
| 2 | 工具名在 `path_scoped` 列表 + 路径不重叠 | 跳过 parallel_safe 检查，允许并行 |
| 3 | 工具名在 `parallel_safe` 列表 | 允许并行 |
| 4 | 其余 | 默认串行 |

配置来源：`[tools.runner]`（见 [配置项参考](../参考/配置项参考.md)）。

执行后经 dispatch 管道推送 `OutputEvent::ToolResult`。

## 中断机制（interrupt）

中断按当前执行阶段分文件处理，每个 handler 读取 `StreamAccumulator` 的部分结果生成中断 ToolResult：

| 阶段 | 文件 | 场景 |
|------|------|------|
| 空闲等待 | `idle.rs` | 等待队列消息时中断 |
| LLM 输出流 | `llm_output.rs` | LLM 正在流式输出 |
| LLM 工具调用 | `llm_toolcall.rs` | LLM 刚返回工具调用，未执行 |
| 工具执行 | `tool_exec.rs` | 工具正在执行 |
| 重试退避 | `retry_backoff.rs` | LLM 调用失败后等待重试 |

`StreamAccumulator` 在流式过程中持续累积已接收的 chunk，中断时读取部分结果，确保不丢失已有输出。

## 安全边界（已知约束）

引擎内核有三处**未设硬上限**的执行路径，目前依赖外部机制兜底：

| 路径 | 缺失的上限 | 当前兜底 |
|------|-----------|---------|
| ReAct 循环 | 无 `max_turns`（轮次计数器） | LoopGuard 的 Abort（interrupt_count ≥ 3）+ 用户 cancel |
| LLM 重试 | 无 `max_retries`（次数硬限） | `on_llm_error` 钩子返回 Abort |
| 工具执行 | 无单工具超时 | 工具内部超时（bash 120s / webfetch 30s / grep 60s） |

> 若 LoopGuard 未加载且无 `on_llm_error` 钩子，理论上可无限循环 / 无限重试 / 工具 hang 住只能靠外部 Interrupt。

### LLM 重试循环

`stream_session` 内部 `'stream: loop` 的重试流程：

```text
provider.stream_chat() → 流事件
    │
    ├── Ok(event) → 正常处理
    │
    └── Err(e)
        │
        ├── !is_retryable（AuthError / ContextOverflow / 4xx）
        │     → 发 Error(recoverable=false) → return Err
        │
        └── is_retryable（429 / 5xx / Timeout / Connection）
              → retry_count += 1
              → 发 Error(recoverable=true)
              → hook_on_llm_error(error, retry_count)
                   │
                   ├── Retry → 标记 Backoff → sleep(退避) → 恢复 Streaming → continue
                   └── Abort → 发 Error → return Err
```

- **无钩子时默认返回 Retry**——即无限重试，退避虽指数增长但永不放弃
- 退避期间可被 Interrupt 命令打断（`retry_backoff.rs` 场景）
- 退避策略见 [Provider 设计](Provider设计.md#重试与退避)

## 关键设计决策

### 为什么双队列（guide + pending）？

- **guide 队列**：高优先级消息，AI 完成一轮对话后立即投递
- **pending 队列**：普通消息，等 AI 不再调用工具（FinishReason::Stop）后才投递

用户可以在 AI 工作时连续发消息，消息按优先级入不同队列，TurnExecutor 有序处理。`QueueUpdate` 事件通知 UI 队列状态（见 [事件协议参考](../参考/事件协议参考.md)）。

### 为什么中断用命令通道而非共享标志？

中断需要实时送达正在 await 的 TurnExecutor。用命令通道（mpsc），`run_turn` 在关键 await 点 `select!` 同时监听 LLM 流和命令通道——中断到达时立即响应，无需轮询标志，零延迟。

### 为什么 dispatch 分 intercept 和完整管道？

用户消息需要入队后才 deliver（延迟 deliver）。`dispatch_intercept` 只做拦截 + 处理（入队），不做 deliver。等 TurnExecutor 从队列取出消息后才走完整 dispatch 管道（含 deliver）。这确保消息按队列顺序投递，不会插队。

### 为什么工具调用要捕获拦截结果？

引擎是消息驱动的——拦截后的消息才是"最终消息"，所有下游模块消费同一份。`stream_session` 对每个工具调用用 `dispatch_intercept`（而非 fire-and-forget 的 `dispatch`），捕获插件修改后的最终版本，用于三个下游：

1. **CLI 显示**（deliver 推送 ToolCall 事件）
2. **会话存储**（AssistantMessage 中的 tool_calls）
3. **工具执行**（orchestrate 用最终参数调用工具）

若用 fire-and-forget 的 `dispatch`，拦截修改只影响显示，执行和存储仍用 LLM 原始参数——三者不一致：插件把 `git` 改成 `rtk git`，但实际执行和数据库里存的还是 `git`。被 Block 的工具调用直接跳过（不执行、不存储）。

### 为什么 core 不持有 tools 的实现？

`SharedTools`（工具表）由 `fuyao-app` 的 `setup` 阶段注入（注册内置工具 + MCP 工具 + 自定义工具），core 只持有引用。引擎内核零感知工具的具体实现——它只知道调用 `ToolFn` 并拿回 `ToolResult`。替换工具集不影响引擎逻辑。

# 核心架构

> 本文解释 fuyao-core 的整体架构设计决策——两层分离、单一入口 / fan-in 出口、session id 全程标签、插件 per-session 实例化、主 / 子 session 区分等核心原则。查 API 签名见 `cargo doc --workspace`；学集成步骤见指南；查配置项 / 字段表见参考。

## 定位

fuyao-core 是**独立 Agent 引擎 SDK**——配置好模型就能跑的 Agent。**支持多 session 并发异步运行**：一个引擎实例同时跑多个对话，互不阻塞。

**设计取向**：

- **多 session 并发**：一个引擎装好能力（启动一次），多个对话按需创建（各自独立 ReAct 循环），靠 session id 区分
- **单 Agent 范畴**：核心只负责单个 Agent 的完整生命周期（ReAct 循环、会话、工具、LLM 调用）；多 Agent 协调、工作流拓扑属于编排层，不在核心
- **对编排零感知**：应用层（CLI / TUI / 服务）依赖 `fuyao-app` 即可，核心代码不含任何编排概念
- **行为可观测**：tracing 日志地基，per-agent 隔离，`RUST_LOG` 可调

## 两层分离（架构基石）

把"引擎能力"与"对话状态"分成两层，是整个架构的核心：

```text
引擎（Engine）              能力共享层 —— 启动一次，装配能力
  ├─ EngineParams           引擎配置（含 agent_paths 等）
  ├─ SessionStore           数据库连接（用 agent_paths 初始化一次，引擎持有，所有 Session 共享）
  ├─ ProviderRegistry       多 Provider 路由（按 provider_id 索引）
  ├─ ToolRegistry           工具注册表（所有 session 共享同一份）
  ├─ PluginHost             插件工厂集合（引擎级模板，每 session 生成独立实例）
  ├─ per-session 出站通道   每个 session 一个无界通道，事件落库后才入 channel（不反压 ReAct）
  └─ sessions 调度表        session_id → SessionHandle（活跃对话登记表）

对话（Session）             交互执行层 —— 按需创建，各自独立
  ├─ session_id             这个对话的唯一编号
  ├─ SessionParams          创建时定死的 Agent 配置（不可变，前缀缓存红线）
  ├─ 消息历史（数据库）      这个对话自己的上下文（事件级落库，按需查询）
  ├─ 数据库访问句柄          从引擎共享而来——用 session id 在同一个库里读写自己的历史
  └─ task 执行流            这个对话自己的 ReAct 循环（双队列 + 中断 + 重试）
```

引擎**先于对话存在**。引擎没启动，谈不上对话；引擎启动后，才能按需创建或恢复任意数量的对话。

## 分层架构

### 五层与依赖方向

11 个 crate 分五层，依赖严格单向（上层 → 下层），无环：

| 层 | crate | 职责 | 内部依赖 |
|----|-------|------|---------|
| **L0 基础** | `fuyao-api` | 公共类型 + 配置系统 + 路径系统 | 无 |
| **L1 能力** | `fuyao-provider` | LLM 抽象 + 供应商注册 + 多 Provider 路由 + 流式调用（reqwest 自建） | api |
| | `fuyao-mcp` | MCP 集成：MCPManager 管理多 Server | api |
| | `fuyao-skills` | Skills 三层发现 + frontmatter 解析 | api |
| | `fuyao-hooks` | 钩子（拦截 + 观察）+ Plugin 两层模型 | api |
| **L2 构建** | `fuyao-prompt` | 提示词分层构建 + Agent 定义加载 | api, skills |
| | `fuyao-guard` | 行为防护：循环检测（Plugin 工厂） | api, hooks |
| **L3 内核** | `fuyao-core` | 引擎内核：Engine（能力共享）+ ReAct 循环（session 执行）+ dispatch 管道 | api, provider, hooks, prompt, session |
| | `fuyao-session` | SQLite 持久化 + 上下文压缩 + 费用统计 + 标题生成 | api |
| | `fuyao-tools` | 内置工具集 + 安全防护 | api, prompt, skills, sqlx |
| **L4 装配** | `fuyao-app` | 装配入口：`start` / `init_engine` / `build_tool_registry` / `shutdown` | 几乎全部 |

> **配置系统在 `fuyao-api/src/config/`，不是独立 crate**——它是类型地基的一部分。
>
> **core 依赖 session**：引擎内核直接持 `SessionStore` 共享 DB 句柄给所有 session。

### L3 内部拓扑

L3 的三个 crate 是兄弟节点，由 L4 装配组合：

```text
L3  fuyao-core（引擎内核）   fuyao-session    fuyao-tools
         │                       │                 │
         │  core 依赖 session      └─────────────────┘
         │  （持 SessionStore 共享 DB）  tools 不依赖 session（todo 自建独立池）
         │
    三者平级，由 L4 fuyao-app 装配组合
```

- `fuyao-core` 依赖 `fuyao-session`：引擎内核直接持 `SessionStore`（事件级落库的统一写入入口），把 DB 句柄共享给所有 session task
- `fuyao-tools` 不依赖 `fuyao-session`：todo 工具自建 `TodoStore` 独立连接池（共用 sessions.db），避免把 sqlx 拖进 L0

## 交互动作 + 单 session 销毁 + 派生

整个使用流程有五个动作（前四个是对话生命周期，第五个是单 session 销毁），另有两个派生动作用于 fork 与子任务场景。应用层一般通过 `fuyao-app::App`（fan-in 单一出口）使用；绕过 `App` 直接用 `Engine` 时，所有创建方法返 `(id, rx)`——rx 由调用方自行消费：

| 动作 | 触发 | 入参 | 返回 |
|------|------|------|------|
| 启动引擎 | 最开始 | `EngineParams` / `ProviderRegistry` / `ToolRegistry` / `PluginHost` | `Engine` 就绪（含 DB 句柄） |
| 创建对话 | 想开新对话 | `SessionParams` | `(session_id, rx)`——主 session 的 rx 进 fan_out，子任务 rx 给调用方 |
| 恢复对话 | 想接着老对话聊 | 老 session id + `SessionParams` | `(session_id, rx)` 重新进调度表 |
| 发消息 | 每次对话 | session id + `InputEvent` | 入队（不阻塞）；模型由 session 的 `SessionParams.model_config` 决定 |
| 销毁单对话 | 关闭某对话保留其他 | session id + end_reason | 该 session 优雅退出 |
| 派生对话（fork） | 从某对话复制可见上下文，开一个独立分支 | 源 session id + `SessionParams` | `(new_id, rx)`（`parent_session_id = None`，独立 session） |
| 创建子任务 session | 后台任务 / 子代理 | 父 session id + `ChildSessionSource` + `SessionParams` | `(new_id, rx)`（`parent_session_id = Some(父 id)`，**rx 不进 fan_out**） |

`ChildSessionSource` 决定子任务的上下文来源：`Fresh`（空上下文，按 `agent_config` 构建 system_prompt）或 `Fork(源 id)`（复制源 session 的可见消息 + system_prompt）。两者产出的 session 都带 `parent_session_id`——区别于纯 fork 的「独立 session」。

引擎关闭**不走消息驱动**——由独立的 `Engine::shutdown()` 方法触发（`App::shutdown` 在其上叠加 forwarder 收尾 + MCP 停机）。

详见 [引擎内核设计](引擎内核设计.md)。

## 单一入口 / fan-in 出口

### 单一入口（send）

所有对话级输入事件从一个口进，靠 session id 区分：

```text
应用层：app.send(session_id, InputEvent)
   │
   ▼
引擎：按 session_id 查调度表 → 路由到对应对话的通道
   ├── User     → tx_inbound 通道 → 触发 ReAct 循环
   ├── Interrupt → tx_interrupt 通道 → select! 中断点响应
   └── Plugin   → tx_plugin 通道 → dispatch 管道 → 发外部
```

`InputEvent` 三个变体（User / Interrupt / Plugin）均为对话级。

### fan-in 出口（App::recv）

出站通道是 **per-session** 的：每个 session task 持一条独立无界通道，事件**落库后**才入 channel（不让 emit 阻塞反压 ReAct turn 推进）。装配层 `App` 为每个**主 session** spawn 一个 forwarder，把 per-session rx 汇聚到单一 `fan_out` 通道，经 `App::recv` 对外暴露统一出口：

```text
session A.task ──► rx_A ──┐
session B.task ──► rx_B ──┼──► [forwarder × N] ──► fan_out ──► App::recv() → Option<OutputEvent>
session C.task ──► rx_C ──┘                                          │
                                                                    ▼
                                                          按 base.session_id 归类
```

**子任务 session（有 `parent_session_id`）不进 fan_out**——`create_child_session` 返 `(id, rx)`，rx 由调用方独占消费：同步子代理 tool handler 用它取最终回复，fire-and-forget 后台任务 spawn 独立 task 消费。这样 UI 出口只暴露主对话，子任务事件不污染主对话流（子代理的中间事件由 handler 经父 session 出站通道转发，session_id 标 child，前端按 child_id 渲染到子代理区域）。

**每条 OutputEvent 都带 session_id 标签**——这是多对话并发不串的底线。事件一产生就带上编号（不是跨边界时才打），消费者拿任意一条事件都能取到 `session_id` 分流，无需匹配。

OutputEvent 共 12 个变体：`Chunk` / `User` / `ToolCall` / `ToolResult` / `Assistant` / `Interrupt` / `Error` / `Plugin` / `Compression` / `Title` / `Retry` / `ChildSession`。详见 [事件协议参考](../参考/事件协议参考.md)。

## 子任务 session：后台任务 / 子代理地基

子任务 session 是带 `parent_session_id` 标记的 session，供前端区分主对话 vs 子任务并按父 id 分组 / 过滤。两类典型用法：

| 用法 | 上下文来源 | rx 消费方 | 典型场景 |
|------|-----------|----------|---------|
| 同步子代理 | `Fresh`（空上下文） | 工具 handler 取最终回复回喂父 ReAct | 父代理调 `subagent` 工具，等子代理跑完 ReAct 拿结果 |
| fire-and-forget 后台任务 | `Fresh` / `Fork` | 独立 task 消费（写日志 / 丢弃——事件已落库） | 后台记忆总结、经验提取（未来扩展） |

子代理的完整流程：父 ReAct 调 `subagent` 工具 → handler 派生子 session（发 `ChildSession(Started)`）→ `send` 任务指令 → 子 session 跑 ReAct，中间事件经父出站通道进 fan_out（session_id 标 child）→ handler 取到最终回复后 `end_session`（发 `ChildSession(Ended)`）+ 返 ToolResult 回喂父。详见 [事件协议参考 — ChildSession](../参考/事件协议参考.md)。

## 并发模型：每 session 一个 tokio task

每个 Session 有自己独立的执行流。多个对话同时活跃时，**它们是并发推进的**——对话A 在想事的时候，对话B 也在想事，谁都不等谁。

对使用者来说，关键就一句：**一个 session 在调工具、在等大模型、在干任何事，都不能卡住别的 session。**

并发分两层，正交不互相协调：

```text
第一层（session 间）：A.task / B.task / C.task 各跑各的（tokio 异步并发）
第二层（session 内）：A 这一批的 a/b/c 工具能并行就并行跑（智能调度 + Semaphore）
```

- **判定是引擎做的，安全是工具自己的**：引擎按配置判定"这一批能不能并行"（只读工具、路径不冲突才并行；有副作用工具如 bash 或路径重叠则整批串行）。判定可并行后用 `Semaphore(max_concurrent=8)` 限流并发跑。
- **两层并发互不协调**：session 内的并发限流是**单次工具执行调用的临时手段**（Semaphore / JoinSet 是函数局部对象，非全局状态），A 的限流管不到 B，B 的也管不到 A。多个 session 同时各自并行调工具叠加起来，引擎依然零协调。

## 核心子系统

### 事件协议

Engine 与应用层之间通过事件通信，单向流：

```text
应用层                     Engine
  │                          │
  ├── InputEvent ──────────► │  （User / Interrupt / Plugin，对话级）
  │                          │
  │ ◄────── OutputEvent ──── │  （Chunk / User / ToolCall / ToolResult /
  │                          │    Assistant / Interrupt / Error / Plugin /
  │                          │    Compression / Title / Retry / ChildSession，12 变体）
```

`EventBase` 是所有事件的公共基座（id + timestamp + session_id）。

详见 [事件协议参考](../参考/事件协议参考.md)。

### Provider 抽象 + 多 Provider 路由

`Provider` trait 统一所有 LLM 供应商（核心方法 `stream_chat` 返回流式事件流）。

引擎不持单个 Provider 实例，而是持 `ProviderRegistry`（按 provider_id 索引的实例集合）。session 的 `SessionParams.model_config.model_id` 形如 `"provider_id/model_id"`——session task 在执行该轮 LLM 调用前拆出 provider_id 从 registry 取实例路由。

**model 配置是对话的属性**：整 session 共享一份 `model_config`，不同对话用不同模型；要切模型调 `Engine::update_session_params`，下一轮自然用新模型（system_prompt 不变，不破坏前缀缓存）。详见 [Provider 设计](Provider设计.md)。

### 会话持久化

会话持久化**由引擎内核直接持有**（`Engine.store: Arc<SessionStore>`）。引擎启动时用 `agent_paths` 找到并打开数据库（所有 Session 的历史都存这同一个库），把数据库访问能力作为引擎级共享。

**事件级落库**：每条消息产生即调 `store.insert_message` 单条 INSERT 进 DB，不进任何内存数组。单个 session 内存占用恒定（不随历史增长），多 session 并发无内存压力。需要消息时按需 `load_visible_messages` 查询。

详见 [会话系统设计](会话系统设计.md)。

### Hooks 与 Plugin

钩子分三类：

| 类型 | 行为 | 执行方式 | 典型用途 |
|------|------|---------|---------|
| **拦截型** | 可修改 / 阻止 | 同步串行，任一 Block 短路 | output_intercept（改写事件） |
| **观察型** | 只读副作用 | 异步串行，发送后执行 | output_observe（持久化、日志、统计） |
| **主动型** | 插件自主发送 | 引擎启动时注入 SessionSender | send_input（插件随时发 User / Interrupt / Plugin） |

所有钩子带 panic 防护 + 可选超时。

**插件 per-session 模型**：插件是 dispatch 管道的延伸能力。多 session 并发时，**每个 session 拥有自己独立的一份插件实例**，互不串台。隔离靠「工厂 + 实例」两层模型实现——引擎级持有工厂模板（`PluginHost`），每 session 启动时调 `create_instance` 生成独立实例。

**统一原则**：插件的一切能力（观察/拦截/发消息）都只能是 hook。没有 hook 之外的"特殊注入通道"。详见 [Hooks 与 Plugin 设计](Hooks与Plugin设计.md)。

## 统一消息处理管道（dispatch）

**所有消息——没有例外——都走同一条管道**，四段串行：拦截 → 处理 → 发送 → 观察。管道在每个 session 内运行（session 层），引擎层只负责装配 hooks 并路由消息到对应 session 的管道。多 session 各自一条独立管道，互不干扰。

```text
任何 OutputEvent（输入转化的、引擎内部产生的）
   ↓
┌─ 拦截（intercept）─┐  插件可修改或阻断（InterceptResult::Block 短路丢弃）
└────────┬───────────┘
         ↓ Block 则丢弃整条（不处理、不发送、不观察）
┌─ 处理（process）───┐  按消息类型的轻量、不阻塞动作：
│                     · User 消息    → 入 guide/pending 队列
│                     · 工具调用消息 → 收集到执行批次（不执行）
│                     · Interrupt    → 投递中断信号
│                     · 其他         → 无处理（透传）
└────────┬───────────┘
         ↓
┌─ 发送（deliver）───┐  经 Emitter::emit 推到单一出口（盖 session_id + tx.send）
└────────┬───────────┘
         ↓
┌─ 观察（observe）───┐  插件只读副作用（持久化/日志/统计）
└─────────────────────┘
```

**进历史的消息**用 `emit_to_history`：拦截 → 用拦截后事件构造 Message 经 `store.insert_message` 单条落 DB → 发送事件 → 观察。所有要落到 DB 的消息必经此入口，保证"拦截 → 存储 → 消费"三者一致。

## 数据流

一条用户消息的完整生命周期（多 session 视角）：

```text
① 应用层：app.send(id, InputEvent::User)
         ↓
② 引擎认编号 → 查调度表（编号 → SessionHandle）
   查不到 → 拒绝（Err(SessionNotFound)，要恢复走恢复动作）
         ↓
③ 路由到对应对话的 tx_inbound 通道（每个对话自己的通道，互不串）
         ↓
④ 该 Session task 从通道取出消息，经 dispatch 管道：
   拦截 → process（入 guide/pending 队列）→ deliver（发 OutputEvent::User 回显）→ observe
         ↓
⑤ 凑历史（从 DB 取该对话的可见消息 load_visible_messages）
         ↓
⑥ resolve_model 拆 model_id → ProviderRegistry 取 Provider 实例
   run_stream_with_retry（react 层重试驱动，发 OutputEvent::Retry）
   用 session SessionParams.model_config 的 thinking 配置 → provider.stream_chat
         ↓
⑦ 边跑边吐，每条产出盖上该对话的编号，经 dispatch 管道送出引擎（主 session 经 fan_out 到 App::recv）
         ↓
⑧ 这一轮聊完，本轮 assistant 消息已在 emit_to_history 落 DB + 累积 session.total_*
```

**热路径（④到⑦）几乎全程走内存 + DB 查询**——不维护内存消息数组。多个对话并发时，各自跑各自的这条线，互不等、互不见。

## 配置两件套（Params）

整个交互流程涉及**两个配置结构体**，职责严格分离，字段不串。命名统一用 `XxxParams` 后缀，是配置两件套：

| 结构体 | 何时提供 | 装什么 | 可变性 |
|--------|---------|--------|--------|
| **EngineParams** | 启动引擎时 | `agent_paths` | 引擎启动时定死 |
| **SessionParams** | 创建对话时 | `agent_config`（definition 等，人格）+ `model_config`（model id / thinking） | `agent_config` 创建时定死；`model_config` 可随时经 `Engine::update_session_params` 切（下一轮生效） |

> 与 TOML 的 `XxxConfig` 严格区分：`Params` 是交互函数的入参，`Config` 是文件配置段，两者语义正交。

**核心判断**：Agent 配置下沉到对话层（`agent_config` 创建时定死，前缀缓存红线），model 配置也下沉到对话层（`model_config` 整 session 共享一份，可随时切）。两者都不留在引擎级——引擎级只装 agent_paths。这样多 session 并发时，不同对话有不同人格（Agent 配置对话级）、不同模型（model 配置对话级），互不干扰；切模型不破坏前缀缓存（system_prompt 不变），故允许运行时 update。

## 扩展点

| 要扩展什么 | 用什么 | 在哪个 crate |
|-----------|--------|-------------|
| 一键启动 / 分步装配 | `start` / `init_engine` / `build_tool_registry` | `fuyao-app` |
| 加自定义工具 | `ToolRegistryBuilder::register` → `Engine::new` | `fuyao-core` |
| 加插件（拦截 / 观察 / 发消息） | `impl Plugin`（工厂）+ `PluginHost::add` | `fuyao-hooks` |
| 接入新 LLM 供应商 | 实现 `Provider` trait + 注册到 `ProviderRegistry` | `fuyao-provider` |
| 加 MCP Server | `[mcp_servers]` 配置 | `fuyao-mcp` |
| 加 Skill | 放三层目录 + SKILL.md | `fuyao-skills` |
| 加 Agent 定义 | `agents/{name}.md` | `fuyao-prompt` |
| 改日志级别 / 输出 | `[logging]` 配置 / `RUST_LOG` | `fuyao-api`(配置) · `fuyao-app`(装配) |

> API 签名见 `cargo doc --workspace`，此处只列扩展点定位。

## 边界禁忌

核心代码不得出现以下概念：

`Workflow` / `Node` / `Edge` / `handoff` / `Master` / `orchestrat`

这些属于编排 / 产品层。核心代码若引入，即破坏边界。

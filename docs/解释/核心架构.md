# 核心架构

> 本文解释 fuyao-core 的架构设计决策。查 API 签名见 `cargo doc --workspace`；学集成步骤见指南；查配置项 / 字段表见参考。

## 定位

fuyao-core 是**独立 Agent 引擎 SDK**——配置好模型就能跑的 Agent。

导入 `fuyao-app` → 填 `AgentContext` → `start()` → 流式对话、工具、技能、MCP、日志全部开箱即用。

**设计取向**：

- **内置电池**：工具（read / write / edit / bash / grep / glob / web 等）、MCP、Skills 全在核心，不要求使用者拼装
- **单 Agent 范畴**：核心只负责单个 Agent 的完整生命周期（ReAct 循环、会话、工具、LLM 调用）；多 Agent 协调、工作流拓扑属于编排层，不在核心
- **对编排零感知**：应用层（CLI / TUI / 服务）依赖 `fuyao-app` 即可，核心代码不含任何编排概念
- **行为可观测**：tracing 日志地基，per-agent 隔离，`RUST_LOG` 可调

## 分层架构

### 五层与依赖方向

11 个 crate 分五层，依赖严格单向（上层 → 下层），无环：

| 层 | crate | 职责 | 内部依赖 |
|----|-------|------|---------|
| **L0 基础** | `fuyao-api` | 公共类型 + 配置系统 + 路径系统 | 无 |
| **L1 能力** | `fuyao-provider` | LLM 抽象 + 供应商注册 + 流式调用（reqwest 自建） | api |
| | `fuyao-mcp` | MCP 集成：MCPManager 管理多 Server | api |
| | `fuyao-skills` | Skills 三层发现 + frontmatter 解析 | api |
| | `fuyao-hooks` | 钩子（拦截 + 观察）+ Plugin 系统 | api |
| **L2 构建** | `fuyao-prompt` | 提示词分层构建 + Agent 定义注册表 | api, skills |
| | `fuyao-guard` | 行为防护：循环检测 | api, hooks |
| **L3 内核** | `fuyao-core` | 引擎内核：dispatch / TurnExecutor(ReAct) / llm / tool_runner / interrupt | api, provider, hooks |
| | `fuyao-session` | SQLite 持久化 + 缓存 + Todo + 上下文压缩 | api, hooks, prompt, provider |
| | `fuyao-tools` | 内置工具集 + 安全防护 | api, prompt, skills, session |
| **L4 装配** | `fuyao-app` | 装配入口：`start` / `init_engine` / `setup` | 几乎全部 |

> **配置系统在 `fuyao-api/src/config/`，不是独立 crate**——它是类型地基的一部分。

### L3 内部拓扑

L3 的三个 crate 并非"core 居中调度 session/tools"。真实的依赖关系：

```text
L3  fuyao-core（引擎内核）   fuyao-session    fuyao-tools
         │                       │                 │
         │  不依赖 session/tools  └─────────────────┘
         │                      tools 依赖 session
         │
    三者平级，由 L4 fuyao-app 装配组合
```

- `fuyao-core` 依赖高度仅为 L1（api + provider + hooks），**不依赖 session 和 tools**
- `fuyao-tools` 依赖 `fuyao-session`（工具需要会话上下文）
- 三者是兄弟节点，仅在 `fuyao-app` 的 `setup` 阶段被组合到同一个 `EngineHandle` 上

**为什么 core 不依赖 session/tools？** 引擎内核只负责消息驱动 + ReAct 循环 + LLM 调用。会话持久化和工具执行是"可插拔能力"，通过 Hooks / Plugin 注入，而非硬依赖。这使得 core 可独立测试，且替换 session / tools 实现不影响引擎逻辑。

> L3 是"角色分层"（引擎内核角色），非严格依赖分层——core 的依赖高度够格放 L2，但角色上属于内核层。

## 双并发 Actor 模型

引擎内核由两个常驻异步任务组成，通过通道通信：

```text
┌──────────────────────┐          ┌──────────────────────────┐
│  Engine              │  命令通道  │  TurnExecutor            │
│  (InputDispatcher)   │ ────────► │  (ReAct 循环)             │
│                      │           │                          │
│  接收 InputEvent      │  队列通知  │  消费双队列消息            │
│  拦截 → 入队 → notify │ ◄──────── │  驱动 LLM + 工具循环       │
└──────────────────────┘           └──────────────────────────┘
```

**Engine（InputDispatcher）**——消息入口。接收 `InputEvent`（用户消息 / 中断 / 插件事件 / 关闭），执行拦截钩子，将用户消息入队（双队列：pending 待处理 + guide 引导优先），通知 TurnExecutor。

**TurnExecutor**——ReAct 驱动。从队列取消息，每轮：准备请求 → before_llm 钩子 → 流式调用 LLM → 中断检查 → 工具执行 → 循环直至 LLM 不再请求工具。

**为什么分两个 actor？** 输入接收与对话推进解耦。用户可以连续发消息（入队等待），TurnExecutor 按队列顺序逐条处理，中断信号经命令通道实时送达正在执行的轮次。

## 核心子系统

### 事件协议

Engine 与应用层之间通过事件通信，单向流：

```text
应用层                     Engine
  │                          │
  ├── InputEvent ──────────► │  （用户消息 / 中断 / 关闭 / 插件）
  │                          │
  │ ◄────── OutputEvent ──── │  （轮次开始 / 文本块 / 工具调用 /
  │                          │    工具结果 / 完成 / 中断 / 错误 /
  │                          │    队列更新 / 插件）
```

`EventBase` 是所有事件的公共基座（UUID + 时间戳），各事件 struct 内嵌为 `base` 字段。

- **InputEvent** 变体：`User` / `Interrupt` / `Shutdown` / `Plugin`
- **OutputEvent** 变体：`TurnStart` / `Chunk` / `User` / `ToolCall` / `ToolResult` / `Assistant` / `Interrupt` / `Error` / `Plugin` / `QueueUpdate`

> envelope / payload 同名靠模块路径区分（`input::UserMessage` 与 `output::UserMessage`），故不在 message 根导出。

### Provider 抽象

`Provider` trait 统一所有 LLM 供应商，核心方法 `stream_chat` 返回流式事件流：

```text
Provider::stream_chat(request, model, options) -> BoxStream<StreamEvent>

StreamEvent = TextDelta | ReasoningDelta | ToolCallChunk | Done
```

内置 `OpenAIProvider`（基于 reqwest 自建 HTTP 客户端，非 async-openai 封装），支持 OpenAI 兼容接口。注册表 `register_provider` / `list_models` 管理供应商与模型，按 agent 路径缓存。

**为什么自建 HTTP？** 流式 SSE 解码 + 重试退避 + 多供应商注册需要细粒度控制，封装库反而碍事。`StreamDecoder` 手写 SSE 解析，`retry` 模块处理退避与可重试判定。

### Session 持久化

`SessionPlugin`（实现 `Plugin` trait）将会话能力注入引擎，而非引擎硬编码依赖：

```text
SessionPlugin 注册的钩子：
  before_llm      → 注入压缩消息 / skip_tools
  output_observe  → 持久化 User / Assistant 消息
  send_input      → 拿 Sender（为压缩后的消息注入做准备）
```

`SessionContext` 管理会话状态（懒初始化：已有 > 加载 > 新建），`SessionManager` 提供全局缓存工厂，`SQLiteStore` 是底层存储（per-agent 隔离）。`CompressionTracker` 检测上下文超阈值并触发 `split_session` 压缩。

**为什么经 Plugin 接入而非引擎内置？** 会话持久化是可选能力。经 Plugin trait 接入，引擎内核零感知存储细节，且替换实现（如换 PostgreSQL）只需替换 Plugin。

### Hooks 与 Plugin

钩子分三类：

| 类型 | 行为 | 执行方式 | 典型用途 |
|------|------|---------|---------|
| **拦截型** | 可修改 / 阻止 | 串行，任一 Block 短路 | before_llm（注入消息）、output 拦截（改写事件）、on_llm_error（重试 / 中止） |
| **观察型** | 只读副作用 | 串行，发送后执行 | output_observe（持久化、日志） |
| **主动型** | 插件自主发送 | 引擎启动时注入 Sender | send_input（插件随时发 InputEvent） |

所有钩子带 panic 防护（`catch_unwind`）+ 可选超时（读 `[hooks] timeout_secs`）。

`Plugin` trait 是编译期扩展点：`impl Plugin` + `PluginHost::install`，按 `[plugins.enabled]` 配置过滤启用。重名硬失败。

> `SharedHooks`（`Arc<Mutex<HooksRegistry>>`）定义在 L1 的 `fuyao-hooks`，`fuyao-core` re-export——为避免环依赖（Plugin trait 签名需要引用它，而 core 依赖 hooks）。

## 数据流

一条用户消息的完整生命周期：

```text
应用层：handle.send_message(InputEvent::User)
   │
   ▼
Engine（InputDispatcher）
   │  拦截钩子 → 入 guide/pending 队列 → notify
   │
   ▼ 命令通道
TurnExecutor 取消息
   │
   ├─► OutputEvent(TurnStart)
   │
   ▼
before_llm 拦截钩子（可注入消息 / skip_tools）
   │
   ▼
Provider::stream_chat（流式调用 LLM）
   │  每个 chunk → OutputEvent(Chunk)
   │
   ▼
LLM 返回 FinishReason
   │
   ├── Stop ──► OutputEvent(Assistant) ──► output 观察 + 拦截钩子 ──► 本轮结束
   │
   └── ToolCalls
          │
          │  每个工具调用经 dispatch_intercept 拦截管道：
          │  插件可修改参数（如 git → rtk git）或 Block 跳过。
          │  拦截后的"最终消息"是下游所有模块的唯一数据源。
          │
          ├─► deliver（OutputEvent::ToolCall 最终版 → CLI 显示 + 观察钩子）
          │
          ├─► emit_assistant_message（AssistantMessage 含最终 tool_calls）
          │         └─► output 拦截 + 观察钩子 ──► 会话存储
          │
          └─► tool_runner::orchestrate（用最终参数执行工具）
                    │
                    ▼
              OutputEvent(ToolResult) ──► output 钩子
                    │
                    ▼
              回到 TurnExecutor 下一轮（ReAct 循环继续）
```

**消息驱动一致性**：工具调用消息在发送前经过 `output_intercept` 拦截管道，拦截后的"最终消息"被统一用于三个下游：CLI 显示（deliver）、会话存储（AssistantMessage 中的 tool_calls）、工具执行（orchestrate）。插件修改参数后三者同步更新，被 Block 的工具调用则跳过（不执行、不存储）。这保证了"参数、结果、记录"三者始终一致。

**中断**：唯一入口 `EngineHandle::cancel` → `InputEvent::Interrupt` → 命令通道 → `run_turn` 在关键 await 点 `select!` 捕获 → 读取 `StreamAccumulator` 部分结果生成中断 ToolResult。

## 扩展点

| 要扩展什么 | 用什么 | 在哪个 crate |
|-----------|--------|-------------|
| 一键启动 / 分步装配 | `start` / `init_engine` / `setup` | `fuyao-app` |
| 加自定义工具 | `EngineHandle::register_tool` | `fuyao-core` |
| 拦截 / 观察 Agent 行为 | Hooks（拦截 / 观察 / 主动） | `fuyao-hooks` |
| 加编译期插件 | `impl Plugin` + `PluginHost` | `fuyao-hooks` |
| 接入新 LLM 供应商 | 实现 `Provider` trait | `fuyao-provider` |
| 加 MCP Server | `MCPManager` 配置 | `fuyao-mcp` |
| 加 Skill | 放三层目录 + SKILL.md | `fuyao-skills` |
| 加 Agent 定义 | `agents/{name}.md` + 注册表 | `fuyao-prompt` |
| 改日志级别 / 输出 | `[logging]` 配置 / `RUST_LOG` | `fuyao-api`(配置) · `fuyao-app`(装配) |

> API 签名见 `cargo doc --workspace`，此处只列扩展点定位。

## 边界禁忌

核心代码不得出现以下概念：

`Workflow` / `Node` / `Edge` / `handoff` / `Master` / `orchestrat`

这些属于编排 / 产品层。核心代码若引入，即破坏边界。

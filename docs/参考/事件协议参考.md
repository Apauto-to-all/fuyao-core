# 事件协议参考

> InputEvent / OutputEvent 全变体与字段参考。字段类型与可空性见 `cargo doc --workspace`，本文只列字段名与业务语义。
>
> **结构约定**：每个事件采用 envelope + payload 两层——envelope（`XxxMessage`）含 `base` 字段，payload（`XxxPayload`）含业务字段。下文逐事件列出字段名（base + payload 平铺，只说业务语义）。

## 事件基座 EventBase

所有事件内嵌 `base` 字段：

| 字段 | 说明 |
|------|------|
| `seq` | 会话内消息序号（Option；仅进历史的事件为 `Some(seq)`，落库时由 store 层分配；不落库的纯实时事件为 `None`。前端据此做游标分页） |
| `timestamp` | 事件时间戳（Unix 纪元秒，f64） |
| `session_id` | 该事件归属的 session id（Option；InputEvent 必填，OutputEvent 由引擎盖标签） |

## InputEvent（UI → Engine）

4 个变体（`#[serde(tag = "type")]`，JSON 序列化带 `type` 鉴别字段）。引擎关闭**不走** InputEvent，由独立的 `Engine::shutdown()` 方法触发。

### User — 用户消息

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息（含 session_id） |
| `content` | 消息文本内容 |
| `images` | 图片附件列表（`[{mime_type, data}]`，`data` 为裸 base64；接受 data URL 或裸 base64 两种入站形态，引擎归一后回显/落库为裸 base64；缺省 `[]`） |
| `mode` | 消息模式（默认 `Guide`） |
| `source` | 消息来源（默认 `User`） |

用户在界面发送消息时携带；也可用于系统注入（超时提醒、错误恢复）或插件注入（循环检测后注入引导消息），由 `source` 区分。图片忠实发送——引擎不做模型能力判断；入站节流（超限压缩 / 处理失败省略并附占位文本）之外不降级，不支持图片输入的模型由服务端返回错误、turn 显式报错。

### Interrupt — 中断

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `reason` | 中断原因描述 |
| `source` | 中断来源（`User` / `Hook` / `Shutdown`） |

用户、钩子、引擎关闭所有中断路径统一走此变体。中断是纯停止信号，不耦合注入消息；如需中断后注入引导消息，额外发送 `User`。

### Compress — 请求压缩

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息（含 session_id） |

用户 / 上层应用主动请求一次上下文压缩。**无业务载荷**——压缩请求只有「现在就压」一个意图，触发参数（模型、上下文长度等）由引擎在执行时按 session 配置现解析。引擎在 turn 边界消费此消息（不抢占在途 turn，等当前 turn 跑完再处理），跳过阈值判定，复用自动压缩的执行流程，触发原因标记为 `manual`。压缩进度仍以三阶段 `OutputEvent::Compression` 回报（见下）。

### Rollback — 请求回退

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息（含 session_id） |
| `target_seq` | 回退到的目标消息 seq（目标本身保留，删 seq > target 的所有消息；目标必须是用户消息或压缩消息，校验在 store 层回退执行体内原子完成） |

用户 / 上层应用请求把会话回退到某条消息。与 `Compress` 同属控制类输入：经引擎入口转控制命令投控制通道，task 在 turn 边界自执行回退（删目标 seq 之后的消息 + 重算会话状态），结果经 per-session 出口以 `OutputEvent::Rollback` 事件流出（见下），不走请求-响应通道。

## OutputEvent（Engine → UI）

12 个变体。每条事件都由引擎盖 `session_id` 标签，多对话并发时 UI 按 `base.session_id` 归类分流。

### Chunk — 流式输出块

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `content` | 文本片段（增量） |
| `reasoning` | 推理片段（增量） |

LLM 流式输出时，每个文本 / 推理片段作为一个 Chunk 推送。两字段可同时为 `None`、同时为 `Some`、或任一为 `Some`。

### User — 用户消息回显

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `content` | 消息文本内容 |
| `images` | 图片附件列表（与输入侧同构，忠实落库 / 发送——UI 所见即用户所发；仅图片处理失败时该图省略并附加占位文本） |
| `mode` | 消息模式 |
| `source` | 消息来源 |

引擎在 `inject_messages` 消费时刻（即把消息真正注入本轮 LLM 输入前）发出，确保引擎处理的内容与 UI 显示的一致。`source` 字段完整保留（含 `Plugin` 来源标识）。

### ToolCall — 工具调用

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `tool_call_id` | 工具调用 ID |
| `tool_name` | 工具名称 |
| `tool_args` | 工具参数（JSON 对象，可为空 `{}`） |

LLM 决定调用工具时，逐个 `dispatch_intercept` 拦截后推送。被拦截 Block 的 tool_call 不发此事件。

### ToolResult — 工具结果

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `tool_call_id` | 工具调用 ID（与对应 ToolCall 配对） |
| `tool_name` | 工具名称 |
| `content` | 工具结果内容 |

工具执行完成后（每完成一个发一个，UX 友好）推送；中断时对未完成的 tool_call 统一补发中断式 ToolResult（content 格式 `[{source}][{reason}]`）。

### Assistant — 助手消息完成

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `content` | 消息内容 |
| `reasoning` | 推理内容 |
| `tool_calls` | 工具调用列表（有 `id` / `name` / `args`） |
| `finish_reason` | 完成原因：`stop` / `tool_calls` / `length` / `content_filter` / `interrupted` |
| `completion_tokens` | 输出 token 数 |
| `prompt_tokens` | 输入 token 数 |
| `total_tokens` | 总 token 数 |
| `reasoning_tokens` | 推理 token 数 |
| `cached_tokens` | 缓存命中 token 数 |

`finish_reason=stop` 为最终回复；`finish_reason=tool_calls` 为工具调用中间轮（后面还有 ToolResult + 最终回复）；`finish_reason=interrupted` 为中断时补发的部分结果消息。

### Interrupt — 中断

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `reason` | 中断原因 |
| `source` | 中断来源 |

引擎中断轮次后发出。所有中断通知（用户 / 钩子 / shutdown）统一走此变体。

### Error — 错误

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `message` | 错误消息 |
| `recoverable` | 是否可恢复（UI 可提示继续） |

异步执行错误（LLM 调用失败、工具执行出错、超长、配置类错误等）经此变体发送。`recoverable=false` 多为严重错误（401/4xx/ContextOverflow）；配置类错误（model_id 格式错、provider 未注册）也走此变体。

### Compression — 上下文压缩（三阶段）

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `payload` | 三阶段 payload 之一（见下） |

单一 `OutputEvent::Compression` 事件，内部 `payload` 区分三阶段（对齐 `UserMessage + UserMessageMode` 模式）：

| payload 变体 | 触发时机 | 关键字段 |
|-------------|---------|---------|
| `Started` | 调摘要 LLM 之前 | `reason`（触发原因：`auto` / `manual` / `overflow`）/ `prompt_tokens` / `context_length` |
| `Delta` | 摘要流式增量（live-only） | `content` / `reasoning` |
| `Ended` | apply 落库成功后 | `reason` / `content`（摘要全文）/ `new_seq` |

`CompressionReason`（触发原因）由 `fuyao-api` 定义：`auto`（上下文 token 超阈值，引擎自动触发）、`manual`（用户 / 上层应用经 `InputEvent::Compress` 主动触发，跳过阈值判定）、`overflow`（预留）。详见 [会话系统设计](../解释/会话系统设计.md)。

### Title — 会话标题更新

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `title` | 新标题（首轮用户消息后异步生成） |

首轮用户消息落库后 fire-and-forget 任务用 fast 模型优先 / 主模型回退生成标题（3-7 词），落库后发此事件。仅基于用户首条消息，不等 AI 回复。失败不发（保留旧标题）。子 session（有 `parent_session_id`）默认不发——`[session.title] skip_child = true` 时跳过，设为 `false` 可关闭此行为。

### Retry — LLM 重试

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `attempt` | 当前重试次数（从 1 开始递增） |
| `max_retries` | 最大重试次数（默认 `u32::MAX`） |
| `wait_ms` | 本次重试前等待毫秒数 |
| `cause` | 错误原因 |

LLM 调用遇可恢复错误（RateLimit / Timeout / Connection / 5xx）后、重试 sleep 之前发送。UI 据此渲染「重试中…N 秒后重试，错误：xxx」提示。严重错误（Auth / 4xx / StreamParseError / ContextOverflow / 首 chunk 后错误）不发 Retry，直接发 Error。

### ChildSession — 子任务 session 生命周期

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息（`session_id` 盖**父** session 标签——事件由父上下文发出，描述 child 生命周期） |
| `parent_session_id` | 父 session id（派生方） |
| `child_session_id` | 子 session id（被派生方——UI 据此过滤后续事件流） |
| `origin` | 派生来源：`Subagent`（子代理工具派生）。后续扩展记忆任务 / 后台任务等来源时在此枚举加变体 |
| `state` | 生命周期状态：`Started` / `Ended` |
| `tool_call_id` | 触发本次派生的 tool_call id（由工具派生时填，非工具派生时为 `None`，序列化时省略） |
| `description` | 任务描述（来自工具参数，供 UI 显示；空字符串序列化时省略） |

派生子任务 session（子代理 / 后台任务 / 记忆总结等）时由派发方发出。UI 据此追踪 child_session_id 并把后续 `base.session_id == child_session_id` 的事件归到此任务的渲染区。

典型消费流：
1. 收到 `ChildSession(Started, child_session_id=X)` → 开辟 X 的渲染区
2. 后续 `session_id == X` 的 Chunk / ToolCall / ToolResult / Assistant → 渲染到 X 的区
3. 收到 `ChildSession(Ended, child_session_id=X)` 或父 ToolResult → 关闭渲染区

子代理场景：父 ReAct 调 `subagent` 工具 → handler 派生子 session → 发 `ChildSession(Started)` → 子 session 跑 ReAct，中间事件经父 session 出站通道进 fan_out（`session_id` 标 child）→ handler 收到最终回复后发 `ChildSession(Ended)` + 父 ToolResult。

### Rollback — 对话回退

| 字段 | 说明 |
|------|------|
| `base` | 事件元信息 |
| `target_seq` | 回退到的目标 seq（位置锚点，回退后它是当前最新消息的 seq） |
| `deleted_count` | 删除的「用户消息数 + 压缩消息数」（界面通知口径，不含附属的 assistant / tool 响应） |
| `deleted_total` | 删除的全部消息数（含 assistant / tool，审计备用） |
| `target_message` | 目标用户消息（`UserPayload` 形态）：user 目标 → `Some`，UI 把 `content` + `images` 填入输入框供重新编辑 / 发送；compaction 目标 → `None`（压缩摘要是助手产出，不填输入框） |
| `message_count` | 重算后的消息总数 |
| `tool_call_count` | 重算后的工具调用总数 |
| `last_compacted_seq` | 重算后的最新压缩边界 seq（删掉所有 compaction 消息时为 `None`） |
| `compression_count` | 重算后的压缩次数 |

对话回退完成后发出。回退 = 删除目标 seq 之后的所有消息 + 重算被影响的统计字段。UI 据此：显示「已回退 N 条」通知（`deleted_count` 口径）、把目标用户消息内容填入输入框（`target_message`）、定位当前会话位置（`target_seq`）。

回退点约束：只能回退到用户消息或压缩消息（assistant / tool 是中间态，回退到它们语义不完整）。校验以 `kind` 为准——压缩消息在 DB 里 `role='assistant'`，靠 role 判会判错。

字段语义两组：`target_seq` / `deleted_count` / `deleted_total` / `target_message` 供 UI 反馈；`message_count` / `tool_call_count` / `last_compacted_seq` / `compression_count` 是重算后的状态值（回退发起方据此刷新内存 session 对象，避免后续落库时把旧值盖回）。消费类字段（token / cost）不在事件中——回退只改消息列表，不否定历史真实消费，这些字段在 DB 里原值保留。

## 共享枚举

### InterruptSource

| 变体 | 说明 |
|------|------|
| `User` | 用户主动中断（Ctrl+C / ESC 等） |
| `Hook` | 钩子拦截中断（循环检测等） |
| `Shutdown` | 引擎关闭时由 shutdown 流程触发，让活跃 session 立即落库退出 |

### UserMessageMode

| 变体 | 说明 |
|------|------|
| `Guide` | 引导模式：进入 guide 队列，触发 ReAct 循环时立即投递（默认） |
| `Pending` | 排队模式：进入 pending 队列，等 AI 不再调用工具（finish_reason=stop）后才投递 |

消费时机：①一批工具全完成后只消费 guide；②最终回复后 pending 全倒 guide 再全取（pending 优先）；③task 空闲时（无活跃链）drain pending 进 guide。

### UserMessageSource

| 变体 | 载荷 | 说明 |
|------|------|------|
| `User` | 无 | 用户主动输入 |
| `System(SystemSource)` | `{ reason }` | 系统注入（超时提醒等） |
| `Plugin(PluginSource)` | `{ name }` | 插件注入（循环检测后注入引导消息等） |

## 与输入事件的对应关系

```text
InputEvent::User     → 经 session task 的 dispatch 管道 → OutputEvent::User（消费时刻回显）
InputEvent::Interrupt → 直接进 tx_interrupt → 触发中断 → OutputEvent::Interrupt
InputEvent::Compress → 进控制通道（turn 边界消费，复用压缩执行流程，reason=manual）→ OutputEvent::Compression
InputEvent::Rollback → 进控制通道（turn 边界消费，删目标消息 + 重算状态）→ OutputEvent::Rollback
```

`InputEvent` 四个变体均为对话级（针对某个 session，靠 `base.session_id` 区分）；`OutputEvent` 12 个变体由引擎统一盖 session_id 标签后流出——**主 session** 的事件经 `App` fan-in 从单一出口 `App::recv` 流出，**子任务 session**（有 `parent_session_id`）的 rx 不进 fan_out，由派生方独占消费（如子代理 tool handler 取最终回复）。

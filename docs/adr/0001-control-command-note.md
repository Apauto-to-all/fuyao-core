# 控制命令附言统一可选、消费自决

控制命令需要承载发送方的补充意图（如手动压缩时指定摘要的侧重要求）。我们决定：附言作为双侧 `ControlMessage.payload.note: Option<String>` 统一可选字段存在，所有命令共享；不落库，随消费回显原样携带。是否消费由各命令执行体自决——多数命令把附言视作一段提示词交给 AI 自行理解，引擎不做解释、改写或过滤。

## 备选方案（否决理由）

- **给每个 `ControlCommand` 变体挂结构化参数**（否决）：每新增一个命令都要动传输构造、输入输出双侧与 IPC 集成方，且多数命令并不需要结构化参数。
- **每个命令独立定义专属消息类型**（否决）：违背「新增控制类功能 = 加 `ControlCommand` 变体，不加新消息、不开新通道」的扩展约定。

## 后果

- 新增命令默认不得把附言设计为必填。确需必填（缺失即无法实现功能）时，由该命令的消费点执行体校验并发 `OutputEvent::Error` 报错；引擎入口不加「哪些命令必填」的策略表——那是命令语义，入口只做形态转化（忠实执行器不变量）。
- 附言不是新的生命周期信号，「新信号首选加事件变体」不变量不适用——它是随行内容而非对外状态变化，故走 payload 字段而非新事件变体。
- wire 格式上附言为 serde 可缺省字段（缺省即 None）。

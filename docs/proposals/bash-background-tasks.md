# 储备提案：bash 后台任务管理

**优先级**：低（储备，供后续参考；需要一套完整的异步任务设计，工作量不小）
**状态**：需求明确，未立项

## 问题

bash 工具目前只有前台 + 超时模式。dev server、watcher、长构建这类长进程无处安放：
要么超时被杀，要么占住整个工具批。Agent 编程场景的刚需是「发起长任务 → 继续干别的
→ 随时回来看输出 / 主动终止」。

## 能力清单（对标主流编码 Agent 的后台任务面）

1. **发起**：bash 工具加 `run_in_background` 参数，立即返回任务句柄（task_id +
   初始输出），不阻塞工具批
2. **列表**：查当前活跃任务（命令、启动时间、累计输出量、退出状态）
3. **读输出**：按 task_id 增量读取（游标式：上次读到的 offset 之后的新输出），
   不全量重传
4. **终止**：按 task_id 杀单个任务；可选「杀全部分会话任务」
5. **终态回收**：任务退出后输出保留一段窗口供回读，超期清理

## 设计要点

- **任务注册表**：进程级内存表（task_id → 子进程句柄 + 输出缓冲游标）。
  是否持久化到磁盘是个决策点——进程重启后僵尸子进程本就不可恢复，持久化
  只为读残留输出，价值有限，建议不持久化（fail-loud：重启后任务即消失）
- **输出落盘**：增量写 `fuyao-agents/{id}/cache/tasks/{task_id}.log`，
  内存只留游标；读输出即读文件区间，内存占用与输出量解耦（对齐「消息不进
  内存」的既有设计哲学）
- **事件面**：任务启动/退出是否发 `OutputEvent` 新变体（消息驱动架构首选加
  变体），还是纯靠工具轮询。倾向：启动/退出发轻量事件（UI 能实时感知任务
  结束），输出内容不推流（按需拉）
- **进程组终止**：Windows 用 Job Object 保证连带子进程一起杀；Unix 用进程组
  (`setsid` + kill pgid)。只杀直接子进程会留孤儿，这是跨平台坑最多的点
- **与会话生命周期的联动**：会话删除 / 引擎 shutdown 时活跃任务怎么办——
  杀（干净）还是过继（可能有意，如用户想让 server 活着）。建议默认杀，
  理由：任务的发起者是 session，session 没了任务语义随之消失；确需长驻
  由上层应用自己起进程，不经引擎
- **停止屏障交互**：`stop_session` 语义是「DB 已静默」，后台任务不属于 DB
  写路径，不影响屏障；但要明确文档化「stop 不杀后台任务，删除才杀」之类的
  边界

## 与核心架构的关系

任务注册表放 fuyao-tools（terminal 模块内），工具上下文
（`ToolCallContext`）注入能力聚合即可，不动引擎内核。唯一的内核牵动是
「任务启动/退出事件变体」（若采用），符合「新生命周期信号首选加事件变体」
不变量。

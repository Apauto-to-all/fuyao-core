# 储备提案：文件编辑随消息回退（git 绑定方向）

**优先级**：低（储备，供后续参考）
**状态**：方向调研完成，未立项

## 问题

`rollback_to` 只回退消息（DB 侧），文件系统的编辑效果不回退。「AI 改坏了代码，
我想连文件一起退回某条消息时的状态」是真实刚需。目标：消息回退与文件回退联动。

## 主流方案调研

| 项目 | 机制 | 特点 |
| --- | --- | --- |
| aider | git auto-commit：每笔编辑自动 commit 到用户仓库，`/undo` = `git reset` | 零自建存储，回退语义就是 git；代价是弄脏用户提交历史（社区长期争论点） |
| Claude Code | 独立快照（非 git commit）：每次编辑前后对被改文件做快照，rewind 时删除其创建的文件、恢复其修改的文件；对话与文件两条回退轴独立 | 不碰用户 git；明确限制：bash 命令产生的文件改动不在追踪内 |
| Cursor | shadow git：项目下建影子 git 仓库存快照 | 不动用户历史；实现较重 |

共同事实：**任何回退机制都需要一份「消息位置 ↔ 文件状态」的日志**（哪条消息对应
哪个文件的什么状态），这部分无法省掉；能做的是把日志薄到只剩引用、把内容托管出去。

## 推荐方向：git 对象库做内容寻址存储

核心思路：**不管理文件内容，只管理引用**。

- 编辑/写入工具成功前，把「编辑前内容」经 `git hash-object -w` 写入对象库
  （workspace 是 git 仓库 → 用户 `.git/objects`；不是 → 在
  `fuyao-agents/{id}/` 下 init 一个私有仓库做对象库）
- 日志只记四元组 `(session_id, seq, path, blob_sha)`——极薄，不存内容文本
- 写一个 ref（如 `refs/fuyao/snapshots/{sha}`）保护 blob 不被 `git gc` 回收
- 回退：`rollback_to(target)` 时取 `seq > target` 的日志条目倒序回放，
  `git cat-file` 取回 blob 内容写回磁盘；新建文件记 tombstone，回退即删除

### 为什么这个形态合适

- **不怕磁盘漂移**：代码被格式化、被其他进程改动，blob 内容不变，回退恢复的
  是快照时刻的内容（与「DB 存 pre-image 文本、内容与磁盘漂移后对不上」的
  表方案本质不同）
- **天然去重**：同一内容反复编辑只存一份 blob（内容寻址）
- **不弄脏用户工作区**：不产生 commit、不动分支、不动 index
- **日志极薄**：四列引用记录，无内容管理负担

### 备选：aider 式 auto-commit

更彻底的 git 路线：专用分支自动 commit，回退 = reset 到对应 commit。实现最省，
但用户历史侵入性强（哪怕是专用分支），与「引擎不自作主张」的气质有张力。
若未来做，应做成显式开关（默认关）。

## 边界清单（立项时必须掰清楚）

1. **覆盖面诚实告知**：仅回退 write/edit 工具的改动；bash 产生的文件操作
   （rm / 生成 / 格式化）不在册——错误信息与文档都要明示
2. **fork 归属冲突**：fork 出的兄弟会话共享同一批文件，一方回退可能覆盖另一方
   的编辑。方案：回退只作用于「本 session 日志记录的编辑」，冲突时（文件当前
   内容 ≠ 本 session 最近一次快照后的预期状态）警告而非静默覆盖
3. **删除会话的清理**：会话级联删除时，对应 ref 与 blob 是否回收（blob 可能被
   多会话共享，需引用计数或延迟 GC）
4. **与压缩的交互**：compaction 边界前后回退目标校验沿用现有 `rollback_to`
   规则，文件侧不感知压缩
5. **并发**：多 session 同时编辑同一文件的日志交错——按 seq 全序回放即可，
   但要接受「后写者胜」的最终状态语义
